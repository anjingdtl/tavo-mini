## 1. 四项问题与修复方式

### 1.1 Checkpoint 主路径摘要密度

**问题**：默认 smart Checkpoint 的 `chapterSummaries` 未完整要求「谁对谁做了什么」等高密度检索字段，主路径与 `generateMemorySummary()` 不一致。

**修复**（`src/services/storyMemory/storyMemoryPrompts.ts`）：

- `STORY_MEMORY_CHECKPOINT_SYSTEM_PROMPT` 增加「逐章检索摘要要求」：主体/行为/对象/结果；承诺/欺骗/冲突/合作/救援/拒绝/背叛；物品获得/失去/使用/转交；信息得知/误解/隐瞒/泄露；关系变化原因；未解决线索/秘密/误会/矛盾；禁止模糊代词；建议 180～320 字（不固定 300）。
- `BATCH_ITEM_CONTRACT` 强化 `brief` / `events` / `characterChanges` / `relationshipChanges` / `newThreads` 写法，**不改 JSON Schema、不增字段**。
- `buildStoryMemoryCheckpointMessages()` user 侧追加检索摘要提醒。

### 1.2 不可用 Story Memory 禁止实体加权

**问题**：`prepareStoryMemoryForGeneration()` 已排除 Dirty，但 `contextBuilder` 又独立 `getProjectStoryMemory` 读 state，可能把过期实体注入 Episodic 加权。

**修复**（`src/services/contextBuilder.ts`）：

- 新增 `resolveStoryStateForRetrieval(prepared)`：仅使用 `prepared.checkpoint.state`。
- `dirty` / `empty` / `failed` / `rebuilding` / 缺失 / 异常 → `storyState = null`。
- 回退：中文 n-gram TF-IDF + 写作要求 + 上一章结尾 + 最近章节桶；**不阻止正文生成**。

### 1.3 Token 预算先优先级筛选

**问题**：候选先按时间升序再塞预算，早期次要长摘要会挤掉高分关键互动。

**修复**（`episodicMemoryRetriever.ts` + `contextBuilder.ts`）：

- 新增 `selectCandidatesWithinTokenBudget(selectedByPriority, budgetTokens)` 与 `formatMemoryCandidateLine()`。
- 流程：混合 Top-K 优先级 → 按优先级预算（超长跳过继续试后续；尚无入选可截断最高优先）→ `orderCandidatesForDisplay()` 按 position 升序展示。
- **未改** `episodicMemoryBudgetTokens` 默认值与其他预算。

### 1.4 共用别名歧义处理

**问题**：`aliasToCanonical: Record<string, string>` 一对一，后写覆盖，导致错误人物/组合奖励。

**修复**（`episodicMemoryRetriever.ts`）：

- `aliasToCanonicalNames: Record<string, string[]>` + `ambiguousAliases`。
- 唯一别名：正常激活与奖励。
- 歧义别名（如两人共用「队长」）：不自动激活、不给人物/组合奖励；仅 query 出现 canonical 名时激活对应人物。

### 性能（30 / 100 / 300 章软阈值，与 V2.5.8 同口径）

- 算法仍近似 O(N)；别名一对多按 alias 建表，非人物数平方。
- 检索路径：混合 Top-K + `selectCandidatesWithinTokenBudget`；软上限 30 章 &lt;500ms、100 章 &lt;1.5s、300 章 &lt;4s（CI 机器浮动）。
- **不增加远程 API**；Android 端无可感知检索卡顿（纯本地评分）。
