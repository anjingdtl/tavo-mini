## 3. 非法 target 以前为何仍能继续构建

`resolveUsableCheckpointForTarget()` 在 V2.5.15 已能识别非法 target（`-1` / `2.5` / `NaN` / `±Infinity`）并返回：

```ts
{ usable: false, reason: 'invalid_position', checkpoint: null, checkpointThroughPosition: -1 }
```

但 `prepareStoryMemoryForGeneration()` 在取得 eligibility 后**仍无条件**调用 `planStoryMemoryCoverage(...)`。当 coverage 无 hardDue 空洞时返回 `blocked: false`，于是 `buildContext()` 继续 Episodic 检索、Renderer、上下文组装，甚至进入正文生成路径。  
**根因**：eligibility 的 `invalid_position` 只用于「不注入 Checkpoint」，未被提升为「目标位置非法 → 禁止构建上下文」。

## 4. target 非法的新阻断路径

```text
prepareStoryMemoryForGeneration()
  → resolveUsableCheckpointForTarget()
  → if reason=invalid_position && invalidPositionSource=target
       return {
         blocked: true,
         blockReason: '目标章节位置无效，无法安全构建上下文。',
         coverage: createEmptyStoryMemoryCoveragePlan('invalid_target_position'),
         checkpoint: null,
         checkpointUpdated: false,
       }
  → (不调用 planStoryMemoryCoverage / advance / rebuild / LLM)

buildContext()
  → prepare(...)
  → if prepared.blocked → throw Error(blockReason)
  → (不进入 Episodic / Renderer / 资源组装)
```

preview 与 generation 均走同一 prepare 入口，均失败。

## 6. `invalidPositionSource` 设计

| 场景 | reason | invalidPositionSource | usable | checkpoint |
| --- | --- | --- | --- | --- |
| target 非法 | `invalid_position` | `target` | false | null |
| through 非法 | `invalid_position` | `checkpoint` | false | null |
| 其它 reason | * | `undefined` | false 或 true | 规则不变 |

`usable=false` 时 `checkpoint` 恒为 `null`；不额外暴露完整 Checkpoint state。诊断仅保留：`reason` / `invalidPositionSource` / `originalStatus` / `originalThroughPosition` / `targetChapterPosition` / `checkpointThroughPosition` / `usable` / `checkpoint=null`。

## 7. 文案差异

| 来源 | `describeCheckpointEligibility()` |
| --- | --- |
| target | **目标章节位置无效，无法安全构建故事上下文** |
| checkpoint | **故事记忆检查点位置无效，本次未注入长期故事状态** |

target 非法**不再**显示为「检查点位置无效」。

## 8. Checkpoint through 非法 fallback

合法 target + 非法 through：

- `checkpoint = null`
- `checkpointThroughPosition = -1`
- **允许** `planStoryMemoryCoverage` 从 -1 规划 raw / episodic fallback
- **`blocked` 不为 true**（solely for through 非法）
- 不注入 Checkpoint、不实体加权

## 9. APK 双份验收逻辑如何合并

**之前**：
1. 测试调用 `Test-ApkSignerAcceptance`
2. 生产主脚本独立 if/throw `V2LineFound` / `VerifiedV2` / `NumberSigners` / 证书比较

**现在**：

- 验收决策**全部**在 `Test-ApkSignerAcceptance`
- Reason：`ok` | `no_v2_line` | `v2_not_true` | `invalid_signer_count` | `no_cert` | `cert_mismatch`
- 成功时用 `NormalizedCertSha256` 填汇总
- 主脚本仍负责：apksigner 进程、退出码、parser、acceptance、汇总、zipalign、aapt、APK SHA-256

## 10. 真实 PowerShell 测试结果

本机 Windows 执行 `__tests__/apkVerificationPowershell.test.ts`（`npm run test:ci` / `test:coverage` / `verify` 内）：

| 场景 | 结果 |
| --- | --- |
| 正常 v2（v1=false,v2=true,signers=1,正确证书） | **Accepted** |
| v1=true / v2=false | **Rejected** (`v2_not_true`) |
| 缺少 v2 行 | **Rejected** (`no_v2_line`) |
| signer=2 | **Rejected** (`invalid_signer_count`) |
| 错误证书 | **Rejected** (`cert_mismatch`) |

主脚本结构契约：必须包含 `Test-ApkSignerAcceptance`；不得独立 `if (-not $parsed.V2LineFound)` / `VerifiedV2 -ne $true` / `NumberSigners -ne 1` / `$certNorm -ne $script:RELEASE_CERT_SHA256_NORM`。

Linux CI 无 PowerShell 时该 describe **skip** 并打日志，不谎报已执行。
