## 6. APK v2 误放行根因

`scripts/verify-release-apk.ps1` 旧版 `Parse-ApkSignerOutput` 的逻辑：

```powershell
$verified = ($v2Line -eq 'true')            # 来自 v2 行
$verifiedAnySchemeLine = (... v\d+ scheme: ...).Count
if (-not $verified -and $verifiedAnySchemeLine -gt 0) {
    $verified = $true                        # 兜底：任意 scheme 行 → true
}
return @{ Verified = $verified; VerifiedV2 = $verified; ... }
```

当 apksigner 输出为 `Verified using v1 scheme: true` / `v2 scheme: false` / `v3 scheme: false` 时：

1. v2 行匹配到 `false`，`$verified=false`；
2. 兜底分支检测到存在任意 `Verified using vN scheme` 行（v1/v2/v3 都算），把 `$verified` 置为 `true`；
3. 返回 `VerifiedV2 = $verified = true`；
4. 主流程 `if ($parsed.VerifiedV2 -ne $true)` 通过，**仅 v1 签名的 APK 被错误放行**。

更严重的是缺行场景：当输出完全没有 v2 行（只有 v1/v3）时，第一个循环不匹配，`$verified` 保持 `false`，兜底再次把它置 `true`，`VerifiedV2=true`。

TS 镜像（`verifyReleaseApkScript.test.ts`）以 `verified = verifiedV2 || verifiedAnySchemeLine` 复现了同一个 bug，所以镜像测试也未能发现。

### 修复

- 解析逻辑拆到 `scripts/apk-verification-parsers.ps1`，返回独立字段 `VerifiedAny` / `V2LineFound` / `VerifiedV2` / `NumberSigners` / `CertSha256`；
- `VerifiedV2` 只来自 `^Verified\s+using\s+v2\s+scheme:\s*(true|false)` 行；v1/v3/v4 行**不得**改变 `VerifiedV2`；缺行 → `V2LineFound=false`、`VerifiedV2=false`；行内 false → `VerifiedV2=false`；
- `VerifiedAny`（任意 scheme true 或 legacy `Verifies`）只作诊断，**不参与**验收决定；
- 主流程硬断言：

```powershell
if (-not $parsed.V2LineFound) { throw "apksigner output does not contain an explicit v2 scheme result" }
if ($parsed.VerifiedV2 -ne $true) { throw "APK must be signed with APK Signature Scheme v2" }
```

继续保持 apksigner 退出码必须为 0、signer 严格等于 1、证书 SHA-256 严格等于固定正式证书、不接受 Debug 签名、不新建 keystore、不输出密码。`Test-ApkSignerAcceptance` 把这套硬断言复刻为纯函数，供真实 PowerShell 测试断言端到端 accept/reject。

## 7. 真实 PowerShell 解析测试结果

`__tests__/apkVerificationPowershell.test.ts` 在本机（Windows 11，`powershell.exe` 可用）通过子进程 dot-source 真实 `apk-verification-parsers.ps1`，对 `Parse-ApkSignerOutput` + `Test-ApkSignerAcceptance` 跑验收矩阵。`findPowerShell()` 优先 `pwsh`、回退 `powershell`，探测命令返回 `OK` 才启用；Linux CI 无 PowerShell 时整组 `describe.skip` 并打印明确日志，**绝不**被谎报为已执行。

本机实际执行结果（PowerShell 子进程，6 个场景各一次 spawn，套件耗时约 25s）：

| 场景 | 输出特征 | V2LineFound | VerifiedV2 | NumberSigners | Accepted | Reason |
| --- | --- | --- | --- | --- | --- | --- |
| 正常 v2 | v1=false v2=true v3=false signers=1 正确证书 | true | true | 1 | **true** | ok |
| 仅 v1 | v1=true v2=false signers=1 正确证书 | true | **false** | 1 | false | v2_not_true |
| 缺 v2 行 | v1=true v3=true（无 v2 行） | **false** | false | 1 | false | no_v2_line |
| 多 signer | v2=true signers=2 | true | true | 2 | false | signers=2 |
| 错证书 | v2=true signers=1 错误 SHA-256 | true | true | 1 | false | cert_mismatch |
| 兜底回归守卫 | v1/v3/v4=true 无 v2 行 | false | false | 1 | false | no_v2_line（`VerifiedAny=true` 仅诊断） |

结论：仅 v1 / 缺 v2 行 / 多 signer / 错证书均被拒绝，正常 v2 通过。真实 PowerShell 测试与 TS 镜像（`verifyReleaseApkScript.test.ts`）现在语义一致。

## 8. target position 合法性定义

`isValidChapterPosition(value)` 是唯一的"合法章节位置"定义：

```ts
function isValidChapterPosition(value: unknown): value is number {
  return (
    typeof value === 'number' &&
    Number.isFinite(value) &&
    Number.isInteger(value) &&
    value >= 0
  );
}
```

同一谓词同时校验：

- 入参 `targetChapterPosition`；
- `state.throughChapterPosition`。

判断顺序（第一个失败的原因胜出，**目标位置合法性最先**）：

1. `invalid_position` — target 非法（即使 checkpoint 为 null）；
2. `missing` — 无 checkpoint 记录；
3. `not_clean` — status !== 'clean'；
4. `empty_state` — state 缺失 / 非对象；
5. `invalid_position` — through 非法；
6. `future_or_same_position` — through >= target；
7. `usable` — 全部通过。

## 9. target 非法矩阵

`__tests__/storyMemoryCheckpointEligibilityV2515.test.ts` 覆盖（每组 × `checkpoint=null` 与 `checkpoint=clean usable record`）：

| target | 期望 |
| --- | --- |
| `-1` | invalid_position |
| `2.5` | invalid_position |
| `NaN` | invalid_position |
| `Infinity` | invalid_position |
| `-Infinity` | invalid_position |
| `"3"` | invalid_position |
| `null` | invalid_position |
| `undefined` | invalid_position |

以上场景均为 `usable=false`、`reason='invalid_position'`、`checkpointThroughPosition=-1`、`checkpoint=null`。并且：

- `target=0` / `through=0` → `future_or_same_position`（不是 invalid）；
- `target=1` / `through=0` → `usable`；
- 非法 target 不会被 `missing`（null checkpoint）/ `not_clean`（dirty）/ `future_or_same_position`（through>target）掩盖——target 校验最先执行。

## 10. unusable checkpoint 状态隔离

`CheckpointEligibilityResult` 改为以 `usable` 为判别的联合类型：

- `usable=true` 分支：`checkpoint: ProjectStoryMemoryRecord`（唯一暴露完整记录的分支）；
- `usable=false` 分支（`missing` / `not_clean` / `empty_state` / `future_or_same_position` / `invalid_position`）：`checkpoint: null`、`checkpointThroughPosition: -1`。

诊断只保留 `reason` / `originalStatus`（标量状态字符串）/ `originalThroughPosition`（数字）/ `targetChapterPosition`（数字）/ `usable`。eligibility 公开结构中**不保留**完整 state / characters / relationships / secrets / objects / plot threads。

## 11. 是否仍能通过任何字段读取未来 state

否。覆盖 `future` / `same-position` / `dirty` / `failed` / `rebuilding` / `empty` / `invalid target` / `invalid through` / `missing` 全场景：

- 运行时：`result.checkpoint === null`（`__tests__/storyMemoryCheckpointEligibilityV2515.test.ts` 每条断言）；
- 类型：`usable=false` 时 `checkpoint` 静态为 `null`，访问 `checkpoint.state` 在编译期即不合法；
- 序列化断言：把整条不可用结果 `JSON.stringify` 后不含敏感标记（`未来秘密-SHOULD-NOT-LEAK` / `未来角色` / `未来地点` / `characters` / `currentState` / `secrets`），证明快照体没有藏进任何诊断字段。

`describeCheckpointEligibility()` 仍只依靠诊断字段（`reason` / `originalStatus` / `originalThroughPosition` / `targetChapterPosition`）生成完整 trace 文案，不读数据库。

## 12. trace 单一事实来源

`buildContext()` 现通过纯函数 `buildStoryMemoryTraceItem({ eligibility, rendererResult, coverage, rawChapterIds, projectId })` 产出**唯一**的最终 story_memory trace 项：

- 不可用 checkpoint：`prepared.checkpoint=null` → Renderer 只看到 missing（空文本、无 tokens）；最终 trace 的 reason 来自 prepared `checkpointEligibility`（真实原因：future / dirty / empty / invalid），不二次读 DB；
- usable checkpoint：reason 为检查点位置，tokens / clipped / preview 来自 Renderer 结果；
- 单次 `buildContext()` 只保留一个最终 story_memory trace 项，不会出现两个互相冲突的 story_memory 条目。

`__tests__/contextBuilderStoryMemoryTraceItem.test.ts` 单独覆盖该纯函数；`storyMemoryPreparedSnapshotIntegration.test.ts` Scenario A/C 继续保证单次 `buildContext()` 只读一次 checkpoint（`getMemoryCallCount - beforeMemory === 1`）。

## 13. build suffix 最终契约

`scripts/generate-version-json.js`（代码逻辑未变，仅修正注释）：

- 显式 `SHINE_WRITER_BUILD_NUMBER`（0–99）**始终**覆盖，优先于任何继承；
- 干净 checkout（无 version.json）或 `version.json.versionName != 当前 package version` → suffix 默认 **0**；
- 同版本重跑（`version.json.versionName == 当前 package version`）且旧 versionCode 含合法 0–99 suffix 且无显式环境变量 → **保留**旧 suffix，避免 versionCode 回退；
- 越界 suffix（如 100）或低于 base 的旧 versionCode → 不继承（suffix=100 会触发单调 versionCode 守卫，按"明确报错"路径 throw）；
- `GITHUB_RUN_NUMBER` 在所有路径继续被忽略。

不再写"只有显式设置时才使用后缀"。

## 14. 环境变量测试

- `GITHUB_RUN_NUMBER=100/999/10000` 不影响 versionCode；
