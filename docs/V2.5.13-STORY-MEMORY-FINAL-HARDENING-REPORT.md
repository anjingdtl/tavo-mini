## 3. 三项生产缺陷的根因和修复

### 缺陷一：人物历史桶回退到姓名字符串匹配（SPEC §5）
**根因**：`ScoredMemoryCandidate` 只存 `matchedCharacters: string[]`（canonical name），混合 Top-K 的人物桶在 `candidateMentionsActiveCharacter` / `activeCharacterCountInCandidate` 没有 `terms` 参数时回退到 `includesInsensitive(candidate.text, name)` 姓名包含判断。重名（`char_reporter.canonicalName === char_doctor.canonicalName === '李明'`）、歧义正式姓名、跨别名场景全部误判。

**修复**：
- `ScoredMemoryCandidate` 新增 `matchedCharacterIds: string[]`，在 `scoreMemoryCandidates()` 内通过 `uniqueNonEmpty(candidateMentions.characterIds.filter(id => activeIdSet.has(id)))` 填充（去重且顺序稳定）。
- `candidateMentionsActiveCharacter(candidate)` 单行实现 `candidate.matchedCharacterIds.length > 0`，删除所有 `active` / `terms` 参数与姓名回退。
- `activeCharacterCountInCandidate(candidate)` 单行 `candidate.matchedCharacterIds.length`。
- 人物桶 sort 中 pair 判定改为 `a.matchedCharacterIds.length >= 2 ? 1 : 0`，不再扫描候选文本。
- 三处 `contextBuilder.ts` 空 candidate 字面量（legacy / `empty_query_recent` / `empty_idf_recent` / `assembleRecentSummariesWithinBudget`）统一补 `matchedCharacterIds: []`。

### 缺陷二：歧义词不占用区间（SPEC §6）
**根因**：`resolveCharacterMentionsInText` 构建 `uniqueTermCandidates` 时 `if (ambiguousNormalized.has(owner.normalizedTerm)) continue;` 把歧义词完全踢出扫描——所以"队长"歧义词不占 `[0, 2)` 区间，内部"长"被后续唯一词扫描误激活。

**修复**：
- 新增导出接口 `CharacterTermScanEntry { normalizedTerm, displayTerm, owners, ambiguous, length }`。
- 按 `normalizedTerm` 建 bucket；唯一词和歧义词共享同一 `scanEntries` 列表，歧义 bucket 保留最长 `displayTerm`。
- 排序：`length` 降序 → 唯一词 canonical 优先于 alias → `normalizedTerm` → `displayTerm`。
- 循环：歧义项把所有未被占用的命中区间加入 `claimedSpans` 并记入 `ambiguousTermsEncountered`，**不创建 mention、不激活任何 characterId**；唯一项照旧激活。
- 结果：`'队长下令，长随后离开'` 中"队长"歧义 → 占区间、不激活，前半段"长"无法命中区间内部；但后半句独立"长"仍被唯一人物激活。

### 缺陷三：单次 `buildContext` 读两次 Checkpoint（SPEC §7）
**根因**：`buildContext()` 调 `prepareStoryMemoryForGeneration()` 拿到 `prepared.checkpoint` 后，又调 `buildStoryMemoryContext()`，后者 `db.getProjectStoryMemory(projectId)` 再读一次。两次读取之间 Checkpoint 状态可能改变（另一进程标 dirty），导致 coverage 用旧 clean、Renderer 因第二次读到 dirty 不注入。

**修复**：
- 新增导出纯函数 `renderPreparedStoryMemoryContext(projectId, currentChapter, checkpoint, budgetTokens, options?)`：**不访问 DB**，只在传入 snapshot 上做防御性 `resolveUsableCheckpointForTarget`，然后走 Renderer + trace。
- `buildStoryMemoryContext()` 降级为薄包装（DB read → `renderPreparedStoryMemoryContext`），仅供没跑过 prepare 的外部调用方使用。
- 主链路 `buildContext()` 内 `storyMemory` 改为 `renderPreparedStoryMemoryContext(projectId, currentChapter, prepared?.checkpoint ?? null, config.storyStateBudgetTokens ?? 8000, { retrievalUserPrompt })`。
- SPEC §7.5 快照一致性不变量成立：`coverage.checkpointThroughPosition` / `resolveStoryStateForRetrieval(prepared)` / Renderer / trace 全部来自同一个 `prepared.checkpoint`。

## 6. 歧义词区间占用规则

### 扫描单元
```ts
interface CharacterTermScanEntry {
  normalizedTerm: string;
  displayTerm: string;        // 最长 surface（同 normalized bucket 内）
  owners: CharacterTermOwner[];
  ambiguous: boolean;         // true 表示不激活但占区间
  length: number;             // displayTerm.length，用于排序
}
```

### 排序
1. `length` 降序（最长词优先）。
2. 等长唯一词条目：canonical 优先于 alias。
3. `normalizedTerm` 字典序。
4. `displayTerm` 字典序。

### 命中规则
- **歧义项**：所有未与 `claimedSpans` 重叠的命中区间 → 加入 `claimedSpans` + `ambiguousTermsEncountered`；**不创建 `CharacterMention`、不激活任何 characterId**。
- **唯一项**：未与 `claimedSpans` 重叠的区间 → 创建 mention、激活唯一 characterId、占用区间。

### 实测覆盖（见 `__tests__/characterHistoryBucket.test.ts`）
- `队长 / 长`：歧义"队长"占 [0,2)；前半段"长"被阻挡；后半句独立"长"激活 `char_chang`。
- `老林 / 林`：同上模式。
- `Captain / captain / Captain队长`：英文大小写共享 normalized `captain`，任何大小写组合不激活任何角色。
- `林岚 / 林`：唯一长词占 [0,2)；独立"林"激活 `char_short`。

## 7. prepared snapshot 一致性

### 主链路（`contextBuilder.ts:buildContext`）
```ts
prepared = await prepareStoryMemoryForGeneration(projectId, currentChapter, config, { mode });
// ...
storyMemory = renderPreparedStoryMemoryContext(
  projectId, currentChapter,
  prepared?.checkpoint ?? null,    // ← 同一份 snapshot
  config.storyStateBudgetTokens ?? 8000,
  { retrievalUserPrompt },

```

### 不变量（SPEC §7.5）
同一次 `buildContext()`：
- `coverage.checkpointThroughPosition`
- `resolveStoryStateForRetrieval(prepared)`（读 `prepared.checkpoint.state`）
- Story Memory Renderer 文本
- trace 中 Checkpoint through

**全部来自同一个 `prepared.checkpoint`**。Renderer 不再读 DB。

### `renderPreparedStoryMemoryContext` 合约
- 纯函数，不访问 DB。
- 内部仅做防御性 `resolveUsableCheckpointForTarget(checkpoint, currentChapter.position)`，不替换为 DB 新值。
- 不可用 → `text === ''` + 单条 trace（reason: `不注入...` / `尚未初始化` / `失效` / `不可用`）。
- 可用 → Renderer 文本 + trace（reason: `检查点截至第 N 章`）。
