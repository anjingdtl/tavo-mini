# Tavo Mini 大纲驱动创作模式分阶段改造方案

> 适用对象：负责在本地仓库中实施改造的开发 Agent / 开发者  
> 目标：为“大纲创作模式”增加独立大纲资源，并使大纲成为整条创作流水线中的最高创作约束。  
> 重要前提：**本地仓库是唯一施工基线。远端仓库、历史分析结果、本文提到的文件名和版本号均只能作为参考，不能直接视为本地现状。**

---

## 1. 改造目标

本次改造需要把“大纲”从当前章节级概要或普通资料，升级为一个独立的一等资源，并贯穿以下完整链路：

1. 资料界面中的大纲管理；
2. TXT 多文件导入；
3. 软件内新建和编辑；
4. 多份大纲独立启用、关闭和排序；
5. 大纲独立上下文预算；
6. 大纲创作模式下的高优先级注入；
7. 初稿、审阅、事实核查、终审全流水线适配；
8. 上下文预览和大纲执行结果展示；
9. 项目导入、导出和迁移；
10. 批量生成、重新生成、任务恢复等边界场景。

最终目标不是“在提示词中多拼接一段文本”，而是建立：

```text
大纲资源管理
→ 大纲上下文构建
→ 大纲驱动初稿
→ 大纲一致性审阅
→ 规划与事实隔离核查
→ 大纲保护型终审
→ 可观察、可验证、可迁移
```

---

## 2. 施工基线原则

### 2.1 本地仓库优先

施工 Agent 必须以当前本地工作区为准，不得默认：

- 本地仓与远端主分支一致；
- 本地仓使用某个固定数据库版本；
- 某个文件或目录仍然存在；
- 当前流水线仍然采用历史分析中的调用结构；
- 本地没有未提交修改；
- 远端最新实现一定比本地更适合。

本方案中的路径和类型名均为**候选定位线索**。Agent 应通过搜索调用链、类型定义和数据库初始化代码自行确认实际位置。

### 2.2 不强制同步远端

除非任务明确要求，否则施工 Agent 不应主动执行：

```bash
git pull
git reset --hard
git checkout .
git clean -fd
```

不得覆盖本地未提交改动。

如需参考远端，可执行只读操作，但必须先确认不会改变当前分支或工作区。

### 2.3 保留现有本地改造

发现以下情况时，应优先兼容，而不是还原成远端结构：

- 本地已有新的资源类型；
- 本地数据库版本高于远端；
- 本地流水线已被重构；
- 本地已有大纲相关实验代码；
- 本地已有未提交 UI 或数据层改动；
- 本地使用了不同的导出协议版本。

### 2.4 禁止硬编码版本假设

本文可能以“新增下一版迁移”为例，但施工时必须动态确认：

```text
当前本地 schema version = N
本次新增迁移 = N → N+1
```

不得直接假定当前版本是某个固定数字。

# 4. 总体设计原则

## 4.1 大纲是独立资源

大纲不应直接复用：

- 笔记；
- 世界书；
- 当前章节简介；
- 预设；
- 故事记忆。

原因：

1. 大纲具有独立开关、顺序和生命周期；
2. 大纲需要独立预算；
3. 大纲是未来剧情规划，不是已发生事实；
4. 后续流水线需要识别其语义；
5. 导出和迁移时必须保留其状态。

## 4.2 大纲是最高“创作意图”，不是最高“事实”

推荐约束优先级：

```text
已经写成且不可回滚的历史事实
> 项目大纲对未来剧情的规划
> 当前章节执行目标
> 本轮用户要求
> 角色卡 / 世界书 / 笔记 / 预设
> 模型自由发挥
```

解释：

- 已经发生的正文不能因为旧大纲而被当作不存在；
- 大纲主导未来剧情；
- 当已写事实与大纲冲突时，应从当前章节开始合理拉回主线；
- 不应让模型为了服从旧大纲而回滚人物记忆、死亡状态或已完成事件。

## 4.3 多份大纲必须确定性合并

建议规则：

```text
按 position 升序
→ position 相同时按稳定 ID 或创建时间排序
→ 列表靠前的大纲优先级更高
```

冲突处理：

- 高位大纲优先；
- 低位大纲只允许补充，不得覆盖；
- 所有大纲必须带清晰分隔和标题；
- 禁止依赖数据库未定义顺序。

## 4.4 大纲默认关闭

新导入或新建的大纲默认不启用，避免未经确认就改变生成结果。

如本地产品现有资源遵循“新建后自动启用”，Agent 可结合产品一致性评估，但必须在施工记录中说明最终选择。

## 4.5 不允许静默截断大纲

大纲具有最高创作约束，静默截断会导致：

- 后半段主线丢失；
- 模型误判结局；
- 后续章节提前或偏航；
- 用户无法判断注入是否完整。

如完整大纲无法放入模型上下文，应：

1. 优先压缩或移除低优先级资料；
2. 仍然放不下时阻止生成；
3. 明确展示大纲 token、可用额度和处理建议。

首版不建议自动调用模型总结大纲，因为总结结果会改变用户原始意图。

# 5. 分阶段实施方案

---

## 阶段 0：基线识别与设计落位

### 目标

确认本地真实架构，输出可执行的本地改造映射，不改业务行为。

### 主要任务

1. 完成第 3 节的本地仓库检查；
2. 绘制本地真实调用链：

```text
资料管理
→ 项目资源关联
→ 上下文构建
→ 初稿
→ 审阅
→ 事实核查
→ 终审
→ 结果采纳
```

3. 确认：
   - 项目模式如何识别；
   - outline 模式是否有别名或已被重构；
   - 流水线是否共享快照；
   - 批量生成是否复用单章流水线；
   - 任务是否可暂停、恢复或重入；
   - 上下文预算是在何处计算；
   - 项目资源是否采用统一关联表。

### 产物

- 本地基线识别报告；
- 本地代码位置映射；
- 数据迁移版本决策；
- 风险清单；
- 实施分支或工作区保护说明。

### 验收

- [ ] 已确定本地所有关键入口；
- [ ] 已确定本地迁移起点；
- [ ] 已确认不需要覆盖本地改造；
- [ ] 已识别所有生成入口，而不只是主按钮。

---

## 阶段 1：数据模型与持久化

### 目标

建立独立大纲实体、项目关联、启用状态和排序能力。

### 推荐数据模型

可采用独立表：

```sql
CREATE TABLE outlines (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id        INTEGER NOT NULL,
  title             TEXT NOT NULL,
  content           TEXT NOT NULL DEFAULT '',
  source_type       TEXT NOT NULL DEFAULT 'manual',
  source_file_name  TEXT,
  position          INTEGER NOT NULL DEFAULT 0,
  estimated_tokens  INTEGER,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  FOREIGN KEY(project_id) REFERENCES projects(id) ON DELETE CASCADE
);
```

但本地仓若采用：

- UUID；
- 字符串时间；
- 通用资源表；
- JSON 数据库；
- ORM schema；
- 独立关联表；

应沿用本地规范，不应为了匹配本文示例而引入第二套模式。

### 启用状态方案

#### 方案 A：大纲表直接存 enabled

适合大纲只属于单个项目：

```text
outlines.enabled
```

#### 方案 B：复用项目资源关联表

适合本地已有统一资源关联机制：

```text
project_resources:
- project_id
- resource_type = outline
- resource_id
- enabled
- position
```

推荐优先沿用本地现有范式。

### 类型调整

需检查并扩展本地对应类型：

```ts
type ResourceType =
  | 'character'
  | 'worldbook'
  | 'note'
  | 'preset'
  | 'outline';
```

不得只改联合类型，还应搜索：

- switch；
- Record<ResourceType, ...>；
- 图标映射；
- 资源名称映射；
- 导出映射；
- SQL 条件；
- 上下文来源枚举；
- UI 筛选；
- 测试 fixture。

### Repository / Service 能力

至少应具备：

```ts
getOutlinesByProject(projectId)
getEnabledOutlinesByProject(projectId)
createOutline(input)
updateOutline(id, patch)
deleteOutline(id)
setOutlineEnabled(projectId, outlineId, enabled)
reorderOutlines(projectId, orderedIds)
```

如本地使用状态仓库或 service 层，遵循现有架构，不新增重复抽象。

### 迁移要求

施工 Agent 必须：

1. 动态读取本地 schema version；
2. 创建 `N → N+1` 迁移；
3. 注册迁移；
4. 更新全新安装 schema；
5. 验证旧数据库升级；
6. 验证重复启动不会重复建表；
7. 验证删除项目后的级联行为；
8. 验证回滚策略或至少保留原数据安全。

### 阶段验收

- [ ] 可创建多份大纲；
- [ ] 可更新标题和正文；
- [ ] 可删除；
- [ ] 可排序；
- [ ] 可独立开关；
- [ ] 新建或导入默认状态符合设计；
- [ ] 旧项目升级后正常打开；
- [ ] 全新安装可直接使用；
- [ ] 本地已有资源未受影响。

---

## 阶段 2：资料界面、导入与编辑

### 目标

在资料入口提供可用的大纲资源管理体验。

### 入口设计

施工时以本地真实资料界面为准。

推荐：

- 大纲创作项目：显示“大纲”页签；
- 原著续写项目：默认不显示“大纲”页签；
- 自由创作项目：可根据产品定义决定是否展示；
- 不要为了加入大纲恢复已经被本地版本删除的旧页面结构。

候选形态：

```text
大纲 | 角色 | 世界书 | 笔记 | 预设
```

如本地使用卡片入口、抽屉或二级页面，应沿用本地交互范式。

### 大纲列表能力

每项至少展示：

- 标题；
- 来源类型；
- 来源文件名；
- 更新时间；
- 估算 token；
- 启用开关；
- 排序位置；
- 编辑入口；
- 删除入口。

建议支持拖拽排序；如本地没有稳定拖拽组件，可首版使用上移、下移。

### TXT 导入

要求：

1. 支持单文件和多文件；
2. 每个 TXT 生成一份独立大纲；
3. 文件名默认作为标题；
4. 自动识别已有文件读取编码能力；
5. 拒绝空文件；
6. 单个文件失败不应使全部文件失败；
7. 导入后展示成功和失败数量；
8. 默认不启用；
9. 保留原始文件名；
10. 重新导入同名文件时不得静默覆盖。

建议复用本地现有文件导入服务，不重复实现：

- 文件选择；
- 本地副本；
- 编码识别；
- 文本读取；
- 错误提示。

### 手动新建

编辑器至少支持：

- 标题；
- 正文；
- 保存；
- 自动保存或离开确认；
- token 估算；
- 启用开关；
- 删除；
- 返回列表。

长文本编辑应重点检查：

- Android 输入法；
- 超长文本性能；
- 页面重建时内容丢失；
- 保存并发；
- 自动保存覆盖；
- 前后台切换。

### 首版不建议实现

- 大纲集合；
- AI 自动解析大纲结构；
- 卷、章自动拆分；
- 自动摘要；
- 大纲版本树；
- 大纲片段向量检索；
- 按章节自动匹配大纲片段。

这些可在核心链路稳定后迭代。

### 阶段验收

- [ ] 可从资料界面进入大纲管理；
- [ ] 可一次选择多份 TXT；
- [ ] 导入后每份文件独立存在；
- [ ] 可在应用内创建和编辑；
- [ ] 开关状态持久化；
- [ ] 顺序持久化；
- [ ] 空文件、读取失败有明确提示；
- [ ] 本地原有资料页功能无回归。

## 阶段 3：大纲上下文构建与预算

### 目标

建立独立的大纲上下文模块，不与普通资源争抢同一预算。

### 独立构建函数

建议新增等价能力：

```ts
buildOutlineContext({
  projectId,
  mode,
  contextWindow,
  reservedOutputTokens,
})
```

返回值建议包含：

```ts
interface BuiltOutlineContext {
  text: string;
  outlineIds: string[];
  outlineVersions: Array<{
    id: string;
    updatedAt: number | string;
    hash: string;
  }>;
  estimatedTokens: number;
  enabledCount: number;
  complete: boolean;
  blockingReason?: string;
}
```

### 仅在适用模式注入

默认规则：

```ts
if (project.mode !== 'outline') {
  return emptyOutlineContext;
}
```

如本地模式名称不同，应映射本地语义，不硬编码旧枚举。

### 拼接格式

建议：

```text
【项目大纲｜最高创作约束】

以下内容用于约束尚未发生的剧情走向。
它不是当前已发生事实，也不代表人物已经知道未来事件。

【大纲 1｜最高优先级】
标题：第一卷主线
正文：
...

【大纲 2｜补充约束】
标题：人物暗线
正文：
...
```

### 大纲合同

建议在系统级指令中加入：

```text
大纲约束规则：

1. 已写成的历史事实不可回滚。
2. 对尚未发生的剧情，必须服从项目大纲。
3. 当前章节目标只能细化大纲，不得改变主线。
4. 角色卡、世界书、笔记和预设不得覆盖大纲主线。
5. 不得提前完成属于后续阶段的关键事件。
6. 多份大纲冲突时，按注入顺序采用靠前内容。
7. 如大纲与既有事实冲突，应从当前状态合理拉回，而不是篡改过去。
```

### 注入位置

推荐把“大纲合同 + 大纲正文”合并到首个系统消息中，而不是简单追加一个靠后的普通消息。

原因：

- 部分兼容模型对多个 system 消息处理不一致；
- 靠后注入可能被章节指令覆盖；
- 高优先级约束应尽早出现；
- 便于上下文预览准确说明。

施工 Agent 应检查本地模型适配层。如模型支持专门的 developer/system 分层，可根据本地 API 调整，但必须保证语义优先级。

### 预算策略

推荐预算顺序：

```text
模型上下文总量
- 输出预留
- 系统协议和基础预设
- 完整项目大纲
- 当前章节执行目标
- 必需的近期正文
- 故事记忆
- 角色 / 世界书 / 笔记
```

禁止：

- 把大纲放入普通 resourceBudget；
- 角色、笔记、世界书先占满预算后再尝试放大纲；
- 无提示截断大纲；
- 只注入前半部分但标记为完整。

### 放不下时的行为

应在任务真正调用模型前中止，并展示：

```text
已启用大纲：3 份
大纲总计：48,200 tokens
当前可用大纲空间：31,600 tokens

请关闭部分大纲、缩短内容，或选择更大上下文模型。
```

### 阶段验收

- [ ] 只有启用的大纲被注入；
- [ ] 拼接顺序稳定；
- [ ] 大纲不计入普通资料预算；
- [ ] 普通资料会优先被压缩；
- [ ] 大纲放不下时阻止生成；
- [ ] 不发生静默截断；
- [ ] 非大纲模式默认不受影响；
- [ ] 上下文构建结果可被后续阶段复用。

---

## 阶段 4：流水线上下文快照

### 目标

让同一次任务的初稿、审阅、事实核查和终审使用相同的大纲版本。

### 快照扩展

本地若存在类似 `PipelineContextSnapshot` 的结构，应加入等价字段：

```ts
interface PipelineContextSnapshot {
  outlineText: string;
  outlineIds: string[];
  outlineFingerprint: string;
  outlineEstimatedTokens: number;

  // 原有字段
}
```

如本地没有统一快照，应先评估：

- 是否可以补充统一快照；
- 是否每个阶段都重新查询数据库；
- 是否存在任务恢复；
- 是否存在并发生成。

推荐在任务开始时冻结大纲内容，而不是每个阶段重新读取。

### 指纹

建议：

```ts
outlineFingerprint = hash(
  enabledOutlines.map(item => ({
    id: item.id,
    updatedAt: item.updatedAt,
    position: item.position,
    contentHash: hash(item.content),
  }))
);
```

任务输入指纹可包含：

```ts
inputFingerprint = hash({
  projectId,
  chapterId,
  chapterUpdatedAt,
  outlineFingerprint,
  contextConfig,
  presetId,
  modelConfigId,
});
```

### 资料变更策略

生成期间用户修改大纲时：

- 当前任务继续使用启动时快照；
- 下一次任务使用新版本；
- 结果采纳前比较指纹；
- 若变化则给出提示，不应静默覆盖。

示例：

```text
生成期间大纲或章节资料已发生变化。
本结果基于任务启动时的版本，请检查后再采纳。
```

### 任务恢复

如本地支持任务恢复，应把以下内容持久化：

- outlineText；
- outlineFingerprint；
- outlineIds；
- 大纲顺序；
- token 统计；
- 阻断状态或构建结果。

恢复任务时不能重新查询当前大纲并替换旧快照，否则恢复前后的阶段可能基于不同规划。

### 阶段验收

- [ ] 同一任务所有阶段使用同一大纲；
- [ ] 运行中修改大纲不改变当前任务；
- [ ] 下一次任务读取新大纲；
- [ ] 恢复任务不重新漂移；
- [ ] 采纳时可检测资料变化；
- [ ] 不影响没有大纲的旧任务。

---

## 阶段 5：初稿阶段适配

### 目标

让初稿真正由项目大纲主导，而不是只依赖章节简介。

### 提示词层级

建议调整为：

```text
【项目大纲｜最高创作约束】
决定尚未发生剧情的主线与阶段方向。

【当前章节执行目标】
说明本章需要完成大纲中的哪一步。

【本轮用户要求】
用于补充表达、节奏和细节，不得改变主线。
```

### 当前章节简介降级

当前章节简介仍然重要，但语义应调整为：

```text
项目大纲在当前章节的局部执行目标
```

不再与项目级大纲并列为同一等级。

### 初稿规则

建议加入：

```text
1. 本章必须服务于项目大纲。
2. 不得自行建立与主线冲突的新主线。
3. 不得遗漏本章应承担的关键推进。
4. 不得提前完成后续章节的关键事件。
5. 必须承接已经写成的前文。
6. 如果前文与大纲存在偏差，应从当前状态逐步拉回。
7. 不得为了服从旧大纲而回滚既有事实。
```

### 章节为空、续写、重写场景

施工 Agent 必须分别验证：

- 空章节从零生成；
- 有正文时继续写；
- 有正文时覆盖重写；
- 仅润色；
- 用户附加本轮要求；
- 章节简介为空；
- 大纲为空但资源存在；
- 大纲全部关闭。

不同生成入口不得漏掉大纲注入。

### 阶段验收

- [ ] 大纲出现在最高优先级位置；
- [ ] 章节简介作为局部执行目标；
- [ ] 本轮要求不能覆盖主线；
- [ ] 空章节和重写均适配；
- [ ] 关闭全部大纲后行为退化为原逻辑；
- [ ] 非大纲模式不被意外注入。

---

## 阶段 6：文学审阅阶段适配

### 目标

使审阅模型能识别偏离、遗漏和过度推进，而不是只检查文风和一般逻辑。

### 新增审阅维度

至少包括：

1. 本章是否完成应承担的主线推进；
2. 是否遗漏必要剧情节点；
3. 是否擅自改变关键事件；
4. 是否过早消耗后续剧情；
5. 新支线是否压制或破坏主线；
6. 人物选择是否仍然服务于大纲；
7. 是否错误回滚既有事实；
8. 是否把大纲中的未来信息写成当前人物认知。

### 推荐结构化结果

如本地支持 JSON 输出，可增加：

```ts
interface OutlineAssessment {
  status:
    | 'aligned'
    | 'partial'
    | 'deviated'
    | 'over_advanced';

  fulfilledBeats: string[];
  missingBeats: string[];
  deviations: string[];
  prematureBeats: string[];
  factRollbackRisks: string[];
}
```

审阅结果：

```json
{
  "strengths": [],
  "issues": [],
  "suggestions": [],
  "outlineAssessment": {
    "status": "partial",
    "fulfilledBeats": [],
    "missingBeats": [],
    "deviations": [],
    "prematureBeats": [],
    "factRollbackRisks": []
  }
}
```

如本地当前只支持自由文本，不要求本阶段强制重构为 JSON，但必须确保终审能够获得清晰的大纲评估。

### 阶段验收

- [ ] Review 能识别偏离；
- [ ] 能识别遗漏；
- [ ] 能识别剧情提前；
- [ ] 能区分正常铺垫和提前完成；
- [ ] 审阅结果能传给终审；
- [ ] 无大纲时保持原审阅逻辑。

---

## 阶段 7：事实核查阶段适配

### 目标

明确区分“未来规划”和“已经发生的事实”。

### 核心语义

大纲中的内容：

```text
是未来剧情规划
不是当前世界状态
不是人物当前知识
不是已经发生的事件
```

### 上下文分区

建议使用明确字段：

```ts
interface FactCheckContext {
  outlinePlanText: string;

  storyMemoryText: string;
  episodicMemoryText: string;
  recentBridgeText: string;
  characterText: string;
  worldbookText: string;
}
```

不要把大纲混入：

- story memory；
- episodic memory；
- current state；
- fact history。

### 核查规则

事实核查必须明确：

1. 大纲可以约束方向；
2. 大纲里的未来事件不能作为当前事实；
3. 未来人物关系不能提前生效；
4. 未来死亡、生还、物品转移、地点变化不能提前生效；
5. 未来秘密不能变成人物当前知识；
6. 事实判断以已写正文和故事记忆为准；
7. 如果初稿提前泄露未来信息，应报告为问题；
8. 如果大纲与已写事实冲突，不应建议回滚历史。

### 阶段验收

- [ ] 不把未来事件判为已发生；
- [ ] 不把未来秘密判为人物已知；
- [ ] 能识别提前生效的状态；
- [ ] 事实判断仍以已写内容为准；
- [ ] 大纲仍可用于判断剧情方向是否违规；
- [ ] 无大纲时保持原行为。

---

## 阶段 8：终审阶段适配

### 目标

终审修正文本时，必须保护已正确执行的大纲节点。

### 终审应保留

- 已完成的关键剧情节点；
- 必需伏笔；
- 大纲指定的人物选择；
- 大纲指定的剧情结果；
- 后续主线依赖的信息；
- 与既有事实相容的主线推进。

### 终审应修正

- 偏离主线；
- 漏写本章必要节点；
- 过早发生的后续节点；
- 将未来规划写成当前事实；
- 为服从旧大纲而回滚历史；
- 无关支线挤占主线。

### 终审不得

- 为了语言流畅删除关键节点；
- 自行改变结局；
- 把大纲中的未来秘密提前公开；
- 以角色卡或笔记覆盖主线；
- 重新解释大纲，使其失去原意。

### 推荐约束结构

```ts
interface ProofConstraints {
  outlineText: string;
  fulfilledOutlineBeats: string[];
  missingOutlineBeats: string[];
  prematureOutlineBeats: string[];
  outlineDeviations: string[];

  // 原有约束
}
```

如本地终审直接消费 Review 和 Fact Check 原始文本，也可先不引入新类型，但必须保证信息完整传递。

### 阶段验收

- [ ] 终审后关键节点仍保留；
- [ ] 缺失节点得到补偿；
- [ ] 提前剧情得到收回；
- [ ] 不把未来规划写成事实；
- [ ] 不回滚既有历史；
- [ ] 无大纲时不改变原终审行为。

---

## 阶段 9：其他生成入口适配

### 目标

避免主流水线已适配，但其他入口绕过新逻辑。

必须逐项检查本地是否存在：

- 单章生成；
- 重新生成；
- 继续写；
- 批量生成；
- 自动连续生成；
- 章节修订；
- 章节扩写；
- 章节缩写；
- 失败重试；
- 任务恢复；
- 草稿重新审阅；
- 仅终审；
- 后台任务；
- 快捷生成入口。

### 批量生成

每章开始时应重新构建该章的上下文，但同一章内部各阶段必须共享快照。

需要明确：

- 前一章完成后，后一章是否读取新的故事记忆；
- 用户在批量任务运行中修改大纲如何处理；
- 是否整批冻结大纲，还是每章冻结一次。

推荐首版：

```text
每章启动时冻结一次大纲快照
同一章内部共享
下一章允许读取最新大纲
```

如产品希望整批结果严格基于同一版本，可改为整批冻结，但必须在 UI 中说明。

### 原著续写模式

默认不注入项目大纲，因为其最高约束通常是：

```text
原著 Canon
→ 已发生事实
→ 当前接缝
→ 原著风格
```

如未来要支持“续写模式的大纲”，应单独设计优先级，不应在本次改造中隐式开启。

### 阶段验收

- [ ] 所有生成入口都经过统一大纲构建；
- [ ] 没有入口直接绕过快照；
- [ ] 批量生成策略明确；
- [ ] 任务恢复策略明确；
- [ ] 原著续写未被意外改变。

type ContextSourceKind =
  | 'outline'

## 阶段 12：项目导入、导出与兼容

### 目标

保证大纲内容、启用状态和顺序可完整迁移。

### 导出内容

至少包括：

```ts
interface ExportedOutline {
  id?: string;
  title: string;
  content: string;
  sourceType: 'manual' | 'txt';
  sourceFileName?: string;
  enabled: boolean;
  position: number;
  createdAt?: number | string;
  updatedAt?: number | string;
}
```

### 协议版本

施工 Agent 必须先检查本地当前导出格式。

原则：

- 如果现有格式有明确版本号，新增不兼容字段时升级协议；
- 不得盲目使用本文或远端曾出现过的固定版本；
- 新版本导入器应兼容旧版本；
- 旧版本应用无法识别新字段时，不应伪装成旧版本导出。

### 导入策略

- 旧项目包没有大纲字段：按空数组处理；
- 新项目包导入：恢复标题、正文、开关、顺序；
- ID 冲突：按本地导入规则重新映射；
- 部分大纲失败：明确报告；
- 不支持的新格式：给出明确版本错误。

### 兼容测试

至少覆盖：

```text
旧项目 → 新版本应用
新项目 → 新版本应用
无大纲项目 → 新版本应用
多份大纲项目 → 导出 → 导入
启用状态 → 导出 → 导入
排序 → 导出 → 导入
```

### 阶段验收

- [ ] 大纲完整导出；
- [ ] 开关完整导出；
- [ ] 顺序完整导出；
- [ ] 旧项目可导入；
- [ ] 新格式可往返；
- [ ] 协议版本基于本地实际值升级；
- [ ] 不静默丢弃大纲。

## 阶段 13：测试、灰度与回滚

### 目标

确保功能可靠，并能在出现问题时关闭或回退。

### 单元测试

建议覆盖：

#### Repository

- 创建；
- 更新；
- 删除；
- 开关；
- 排序；
- 项目删除级联；
- 默认状态；
- 多项目隔离。

#### 上下文构建

- 多份拼接；
- 稳定排序；
- 只取 enabled；
- 非大纲模式为空；
- token 计算；
- 预算阻断；
- 指纹稳定；
- 内容变化后指纹变化。

#### 流水线映射

- Draft 获得大纲；
- Review 获得大纲；
- Fact Check 获得规划分区；
- Proof 获得大纲和审阅结果；
- 同一任务共享快照。

### 集成测试

至少包含：

1. 导入两份 TXT；
2. 只启用其中一份；
3. 生成章节；
4. 验证请求中只包含启用项；
5. 调整顺序；
6. 再次生成；
7. 验证顺序变化；
8. 生成期间修改大纲；
9. 验证当前任务仍使用旧快照；
10. 验证结果采纳前出现变更提示。

### 关键语义用例

#### 用例 A：大纲与角色卡冲突

```text
大纲：主角决定离开故乡。
角色卡：主角极度恋家。
```

期望：角色性格影响表现方式，但不能阻止主线事件。

#### 用例 B：大纲与已发生事实冲突

```text
已写正文：导师已经死亡。
旧大纲：导师在后续现身并指认真凶。
```

期望：不得让导师直接复活。应提示冲突，或通过遗信、录影等方式合理拉回。

#### 用例 C：未来秘密

```text
大纲：第 30 章揭示父亲是幕后主使。
当前：第 10 章。
```

期望：事实核查不得认为主角已经知道真相；初稿不得提前揭示。

#### 用例 D：多份大纲冲突

```text
高优先级：主角拒绝加入组织。
低优先级：主角加入组织。
```

期望：采用高优先级，低优先级仅可作为冲突提示。

#### 用例 E：大纲超长

期望：普通资料先压缩；仍放不下则生成前阻断。

### 性能测试

- 10 份大纲；
- 单份大纲超长文本；
- 多文件导入；
- 长文本编辑；
- 上下文预览；
- 数据库查询；
- 批量章节生成。

### 功能开关

建议增加本地 feature flag：

```ts
outlineResourceEnabled
outlineStrictInjectionEnabled
outlinePipelineReviewEnabled
```

如本地没有功能开关框架，可至少保证：

- 关闭大纲时原逻辑可运行；
- 数据迁移不依赖 UI 开关；
- 紧急情况下可隐藏入口但不删数据。

### 回滚原则

回滚时优先：

1. 关闭入口；
2. 停止注入；
3. 保留数据库和用户大纲数据；
4. 不降级删除表；
5. 不丢弃导入内容。

### 阶段验收

- [ ] 单元测试通过；
- [ ] 集成测试通过；
- [ ] 旧模式回归通过；
- [ ] 迁移测试通过；
- [ ] 导入导出往返通过；
- [ ] 可关闭功能且不丢数据；
- [ ] 本地未提交改动仍被保留。

# 7. Agent 施工决策规则

施工 Agent 遇到本文与本地代码不一致时，按以下顺序处理：

```text
本地运行行为
> 本地类型和数据库约束
> 本地未提交改动
> 本地测试
> 本地已提交架构
> 远端当前实现
> 本文示例路径和版本
```

## 7.1 可以自行调整的内容

- 文件路径；
- 类型名称；
- Repository 命名；
- schema 版本号；
- 导出协议版本；
- UI 组件拆分方式；
- 状态管理接入方式；
- 测试文件位置；
- 数据库字段类型。

## 7.2 不应自行改变的核心需求

- 大纲为独立资源；
- 支持 TXT 多文件导入；
- 支持应用内新建和编辑；
- 多份大纲可独立开关；
- 多份大纲具有稳定顺序；
- 只有启用项被注入；
- 大纲不与普通资料共享预算；
- 大纲不能被静默截断；
- 大纲贯穿 Draft、Review、Fact Check、Proof；
- 大纲是未来规划，不是已发生事实；
- 已发生事实不可被旧大纲回滚；
- 导入、导出保留内容、开关和顺序；
- 非大纲模式不得被意外改变。

## 7.3 必须暂停并报告的情况

遇到以下情况时，Agent 不应猜测性大改，应在施工报告中明确说明：

- 本地存在两套并行流水线，无法判断实际入口；
- 本地数据库迁移链已断裂；
- 项目导出格式没有版本机制；
- 本地已有大纲表但语义完全不同；
- 生成请求绕过统一上下文层；
- 本地测试无法运行且原因不明；
- 工作区存在与本次改造重叠的大量未提交修改；
- 上下文窗口和 token 预算无法从模型配置中获得；
- 任务恢复机制无法持久化大纲快照。

在不破坏现有代码的前提下，可先完成独立阶段并记录阻塞项。

## 结论

本次改造应被视为一次“创作约束体系升级”，而不是普通资料功能扩展。

施工时必须坚持两条底线：

```text
第一，本地仓库和本地运行行为是唯一事实来源。
第二，大纲必须贯穿完整流水线，而不是只在初稿提示词中出现。
```

只要按阶段完成数据、UI、上下文、流水线、预览、迁移和测试，大纲创作模式才能真正实现“由大纲完全主导未来小说主线，同时不破坏已经写成的事实”。
