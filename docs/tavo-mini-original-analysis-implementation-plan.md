# Tavo Mini 原著分析质量改造实施方案

> 目标：在不限制模型推理与输出能力的前提下，通过更小的原著正文切块、更多轮 API 调用、严格 JSON 校验、可靠物化与最终五维验收，确保完整分析和快速续写分析都能独立产出可直接用于 AI 续写的高质量原著分析资料。

## 1. 改造结论

本次改造采用以下最终规则：

1. **模型能力不设限**
   - 使用 LLM 配置声明的真实上下文窗口。
   - 使用 LLM 配置声明的最大输出额度。
   - 保持模型原有思考模式，不为原著分析主动关闭推理。
   - 不设置 Canon/原著分析专用的输出硬上限。

2. **30%只用于原著正文切块**
   - 单批原著正文目标大小为：`LLM context_window × 30%`。
   - 30%不是模型上下文配置，不写回 LLM 配置。
   - 30%不用于压缩 `max_output_tokens`，不限制思维链长度。
   - 遇到超长、截断或空响应时，只缩小失败批次的正文，不降低模型能力。

3. **两种分析模式完全独立**
   - 完整分析：分析导入 TXT 的全部章节。
   - 快速续写分析：只分析导入 TXT 的最后 10 章，并进行精读。
   - 两种模式不读取、不继承、不合并对方的分析结果。
   - 两种模式都独立生成完整五维资料并独立验收。

4. **续写读取不区分分析模式**
   - 两种模式产出相同的数据结构和查询契约。
   - 任一模式成功后，其产物都可成为当前激活的原著分析产物。
   - AI 续写只读取当前激活产物，不根据 `full/quick` 分支处理。
   - 失败运行不得替换已有的成功产物。

5. **五维最终硬验收**
   - 人物资料不少于 3 条。
   - 世界观规则不少于 3 条。
   - 人物关系不少于 3 条。
   - 剧情线不少于 3 条。
   - 人物经历不少于 3 条。
   - 统计对象必须是当前运行最终去重、证据校验通过、成功物化并可回读的有效数据。
   - 任意一维不足 3 条，分析不得标记完成，不得激活，不得用于续写。

---

## 2. 问题背景

当前原著分析链路已经具备模型调用、JSON 解析、证据校验和 Canon 表物化能力，但仍存在以下质量风险：

- 超长上下文被尽量填满，单次分析任务颗粒度过大，模型注意力分散。
- 一次请求承担过多维度，部分维度可能被直接返回为空数组。
- 模型返回合法但全空的 JSON 时，系统可能错误地视为成功。
- 模型原始 JSON 已保存，不代表有效信息已经成功物化到数据库。
- 证据定位失败可能让模型输出的条目在物化前被全部过滤。
- 最终五维全空或数量严重不足时，运行仍可能完成并激活。
- 快速分析使用最后 30 章，范围过宽，不利于续写前的近期状态精读。

本次改造的核心不是追求更少的调用次数，而是明确接受更多 API 调用，以换取更高召回率、更稳定的 JSON 和更可靠的最终资料。

## 3. 术语与数据范围

### 3.1 分析模式

```ts
type OriginalAnalysisMode = 'full' | 'quick';
```

- `full`：完整原著分析。
- `quick`：快速续写分析。

模式只决定：

- 本次选择哪些原文章节；
- UI 展示的模式名称；
- 运行元数据和审计信息。

模式不改变：

- 五维输出 Schema；
- 物化表结构；
- 最终验收门槛；
- AI 续写读取方式。

### 3.2 五维资料

本次硬验收只针对用户可见的五个维度：

```ts
type RequiredCanonDimension =
  | 'characters'
  | 'world_rules'
  | 'relationships'
  | 'plot_threads'
  | 'experiences';
```

内部仍可继续生成知识、状态、时间线等辅助资料，但它们不代替五维最低数量验收。

### 3.3 有效信息

一条记录只有同时满足下列条件，才计入最终数量：

1. 来自当前分析运行和当前快照；
2. JSON Schema 校验通过；
3. 必填字段完整；
4. 至少一条证据成功解析并能映射回本次原文范围；
5. 经过去重后仍被保留；
6. 已在数据库事务中成功写入；
7. 写入后按快照重新查询能够读取；
8. 未被标记为删除、无效或 superseded。

模型原始数组长度和 `result_json` 中的条目数量不能直接作为最终验收数量。

## 4. 总体处理架构

每次分析运行采用统一流水线：

```text
选择分析范围
  ↓
按上下文 30% 规划正文批次
  ↓
每批并行执行两路分析
  ↓
响应完整性检查
  ↓
JSON 解析与字段归一化
  ↓
Schema 校验
  ↓
证据解析
  ↓
批次级去重与合并
  ↓
当前快照数据库物化
  ↓
物化后回读验证
  ↓
全运行合并与最终去重
  ↓
五维数量验收
  ↓
缺失维度定向补扫
  ↓
再次物化、回读、验收
  ↓
成功则原子激活，失败则保留旧产物
```

建议保持现有双路并行设计：

### 路线 A：人物与状态

负责提取：

- 人物；
- 人物关系；
- 人物经历；
- 人物知识；
- 人物状态。

### 路线 B：世界与剧情

负责提取：

- 世界观规则；
- 剧情线；
- 时间线事件。

两路是两个独立请求，单请求分别遵守模型上下文限制；不得把两路并发请求的 token 相加后当作一个上下文窗口处理。

## 5. 两种模式的执行定义

## 5.1 完整原著分析

### 原文范围

```ts
selectedChapters = allImportedChapters;
```

要求：

- 覆盖导入 TXT 中的全部有效章节；
- 不因章节数量多而跳过中间章节；
- 超长章节必须拆分，不能跳过；
- 所有批次最终合并为当前完整分析快照。

### 结果语义

基于整个导入 TXT，独立生成一套完整五维资料。

### 最终验收

当前完整分析快照中五维每维至少 3 条有效信息。

## 5.2 快速续写分析

### 原文范围

```ts
selectedChapters = allImportedChapters.slice(-10);
```

边界规则：

- 原著不足 10 章时，分析现有全部章节；
- 最后 10 章在切块前确定；
- 不得为了填满 30% token 目标而向前追加第 11 章或更早章节；
- 单章超长时可在该章内部继续切块；
- 章节顺序保持原始顺序。

### 结果语义

基于最后 10 章，独立重建一套可直接用于下一章续写的完整五维资料，而不是完整分析的增量或补丁。

### 最终验收

当前快速分析快照中五维每维至少 3 条有效信息。

### 独立性要求

快速分析不得：

- 读取完整分析快照作为提取输入；
- 使用完整分析的数据补足最低数量；
- 继承完整分析的成功状态；
- 将完整分析表中的记录计入本次验收。

完整分析同样不得借用快速分析结果。

## 6. 30%正文切块算法

## 6.1 核心原则

设：

- `C`：LLM 配置声明的 `context_window`；
- `O`：LLM 配置声明的 `max_output_tokens`；
- `P`：本次请求提示词、JSON Schema、章节元数据等输入开销；
- `S`：本批原著正文 token 数。

正文目标值：

```ts
const sourceChunkTargetTokens = Math.floor(C * 0.30);
```

该值只控制 `S`，不改变 `C` 和 `O`。

## 6.2 请求能力保持完整

请求参数原则：

```ts
request.max_tokens = configuredMaxOutputTokens;
request.thinking = configuredThinkingMode;
```

禁止：

- 使用 `C × 30%` 作为请求上下文上限；
- 使用 `O × 30%` 作为最大输出；
- 为 Canon 单独设置 64K、96K 等输出天花板；
- 因分析模式自动关闭思考模式；
- 用内部“安全预算”覆盖用户配置的模型能力。

## 6.3 协议兼容性处理

如果某服务商明确要求“输入 token + 最大输出 token”不能超过上下文窗口，则只允许缩小正文：

```ts
const protocolInputLimit = C - O - P;
const actualSourceLimit = Math.min(
  sourceChunkTargetTokens,
  protocolInputLimit,
);
```

要求：

- 不降低 `O`；
- 不关闭 thinking；
- 不写回或篡改 LLM 配置；
- 该限制属于协议兼容性处理，不得再额外乘 80%、60% 等内部比例；
- 若配置本身导致没有任何可用输入空间，应明确报告配置不兼容，而不是静默修改模型能力。

对于允许服务端动态使用输出的兼容接口，可直接以 30%正文目标发送请求，同时保留完整输出配置。

## 6.4 章节优先切块

规划顺序：

1. 按章节顺序估算 token；
2. 尽量保持完整章节；
3. 加入下一章会超过目标值时，结束当前批次；
4. 单章大于目标值时，在该章内部切块；
5. 不跳过任何选定章节；
6. 批次记录精确的章节和字符范围，供证据定位使用。

## 6.5 失败后的缩块

30%是正常运行的最大目标，不是所有重试必须达到的固定大小。

以下情况可只对失败批次缩小正文：

- `finish_reason = length`；
- 只有思维链，没有最终业务 JSON；
- JSON 被截断；
- 路线负责的全部分类为空；
- 证据解析后全部条目被过滤；
- 请求超时或服务端内存压力明显。

建议重试阶梯：

```ts
const retryChunkRatios = [0.30, 0.20, 0.12];
```

每次只缩小原文输入，模型的 thinking 和最大输出保持不变。

## 7. LLM 请求与提示词要求

## 7.1 模型参数

原著分析不得主动降低模型能力：

- 保持用户配置的模型名称；
- 保持用户配置或模型默认的思考模式；
- 传递完整 `max_output_tokens`；
- 保持现有合法的采样参数策略，除非模型官方明确忽略；
- JSON 模式可在服务商支持时启用；
- 服务商不支持 JSON 模式时可回退为严格文本 JSON 提示，但不能改变输出 Schema。

## 7.2 输出约束

每个响应必须：

- 只返回一个完整 JSON 对象；
- 所有规定数组字段必须出现；
- 不允许 `null` 代替数组；
- 每条记录使用明确的字段名；
- 每条有效信息必须提供证据；
- 不允许使用外部知识补写；
- 不允许为满足最低数量而编造内容。

最低 3 条是系统最终验收条件，不是模型的自由生成配额。

## 7.3 模式提示

完整分析提示中应明确：

> 当前输入是全文分析中的一个批次，只提取本批原文明确支持的事实，系统将在全部批次完成后合并。

快速分析提示中应明确：

> 当前输入属于原著最后 10 章精读范围，请基于这 10 章独立重建可支持下一章续写的五维资料，不得假设存在其他分析结果。

不得在快速分析提示中使用“增量”“相对于已有 Canon”等措辞。

---

## 8. JSON 解析与响应质量门

## 8.1 响应完整性检查

以下情况不得直接标记工作项成功：

- 没有 choices；
- 最终 `content` 为空；
- 只有 `reasoning_content`；
- `finish_reason = length`；
- JSON 对象不完整；
- JSON 无法解析；
- 路线负责的所有分类总条数为 0；
- Schema 校验后路线负责的所有分类总条数为 0；
- 证据解析后路线负责的所有分类总条数为 0。

上述情况进入可重试失败，不得静默完成。

## 8.2 允许的安全归一化

可进行：

- 去除 Markdown JSON 代码围栏；
- 提取唯一的顶层 JSON 对象；
- 兼容已知字段别名；
- 将明确可转换的标量标准化为预期类型；
- 补齐缺失但可确定为空的非当前路线数组字段。

不得进行：

- 根据自然语言自行生成缺失事实；
- 在证据缺失时伪造证据；
- 为达到最低数量复制或改写已有条目；
- 将解析失败的内容当作成功保存。

## 8.3 全空检测

当前路线的空结果应按路线所有权判断：

```ts
const ownedTotal = ownedCategories.reduce(
  (sum, category) => sum + validated[category].length,
  0,
);

if (ownedTotal === 0) {
  throw new RetryableEmptyExtractionError();
}
```

不要再要求 `received > 0` 才触发空结果重试。

## 9. 证据解析设计

## 9.1 原则

证据是有效信息的必要条件，但证据定位失败不能被隐藏。

每条证据至少包含：

- 章节标识；
- 原文连续引用；
- 原文范围或可解析定位信息。

## 9.2 推荐定位方式

优先让模型返回：

- 章节 ID 或章节位置；
- `quotePreview` 原文连续片段。

绝对字符偏移建议由本地程序根据章节正文确定：

1. 在声明章节中进行精确匹配；
2. 处理常见换行和空白归一化后再次匹配；
3. 必要时进行受控的近似匹配；
4. 匹配唯一时生成绝对 UTF-16 偏移；
5. 多处匹配或无法匹配时标记该证据失败。

不要把复杂的绝对偏移计算完全依赖模型完成。

## 9.3 证据失败统计

每批必须记录：

- 模型收到条目数；
- Schema 接受条目数；
- 证据解析成功条目数；
- 去重后保留条目数；
- 实际物化条目数。

当某路线模型有输出但证据后为 0 时，必须作为可重试失败处理。

---

## 10. 合并与去重

## 10.1 运行隔离

所有合并仅处理当前：

- `project_id`；
- `run_id`；
- `snapshot_id`。

不得从其他模式、其他运行或旧快照补数据。

## 10.2 去重目标

至少处理：

- 同一人物的别名合并；
- 同一人物关系的重复表述；
- 同一世界规则的近义重复；
- 同一剧情线在多个批次中的重复节点；
- 同一人物经历的重复事件；
- 相邻切块重叠导致的重复证据。

## 10.3 去重后验收

最低 3 条必须在最终去重后计算。

重复条目不能通过改写标题或摘要被重复计数。

---

## 11. 数据库物化与回读确认

## 11.1 保存顺序

建议使用事务完成当前批次或当前快照的物化：

```text
保存原始响应与解析统计
  ↓
写入五维及辅助 Canon 表
  ↓
写入证据表或证据字段
  ↓
更新工作项物化状态
  ↓
提交事务
```

`result_json` 保存成功不等于分析数据成功。

## 11.2 物化后回读

每次物化后必须按当前快照重新查询计数：

```ts
const persistedCounts = await countValidCanonRows({
  projectId,
  snapshotId,
});
```

至少验证：

- 写入行数与物化器报告一致；
- 五维页面使用的查询接口能够读取；
- 不存在 JSON 有数据、Canon 表为 0 的情况；
- 不存在插入到错误快照或旧快照的情况。

## 11.3 有效行过滤

最终计数应与五维页面实际展示逻辑一致，排除：

- superseded；
- invalid；
- deleted；
- 证据无效；
- 不属于当前快照的数据。

## 12. 五维最终验收与定向补扫

## 12.1 最终验收门槛

```ts
const REQUIRED_MIN_COUNT = 3;

const passed = requiredDimensions.every(
  dimension => finalPersistedCounts[dimension] >= REQUIRED_MIN_COUNT,
);
```

五维必须分别满足：

```text
characters    >= 3
world_rules   >= 3
relationships >= 3
plot_threads  >= 3
experiences   >= 3
```

## 12.2 验收时机

验收必须发生在：

- 所有正常批次完成；
- 所有响应解析完成；
- 证据解析完成；
- 全运行去重完成；
- 数据库物化完成；
- 数据库回读完成。

不能在模型原始 JSON 阶段提前通过。

## 12.3 定向补扫

若某些维度不足 3 条，则只针对缺失维度重新扫描当前模式的原文范围：

```ts
const missingDimensions = requiredDimensions.filter(
  dimension => finalCounts[dimension] < REQUIRED_MIN_COUNT,
);
```

补扫要求：

- 完整分析仍扫描全文范围；
- 快速分析仍扫描最后 10 章范围；
- 不读取另一个模式的数据；
- 提示词只聚焦缺失维度；
- 正常目标仍不超过上下文的 30%；
- 可对失败批次进一步缩小到 20% 或 12%；
- 保持完整模型输出与思考能力；
- 新结果继续走 Schema、证据、去重、物化和回读流程。

建议每个缺失维度最多执行 2 轮定向补扫，避免无限调用。该次数应定义为可配置常量。

## 12.4 最终失败

补扫结束后任一维度仍不足 3 条：

- 运行状态标记为 `failed`；
- 保存实际计数与失败维度；
- 不激活当前快照；
- 不覆盖上一个成功分析产物；
- UI 明确提示哪些维度不足；
- 不允许显示“分析完成”。

不得让模型编造信息补足数量。

---

## 13. 快照激活与 AI 续写读取

## 13.1 统一产物契约

完整分析和快速分析都生成同一种 Canon 快照结构。

快照可保留以下元数据用于审计和 UI：

```ts
interface OriginalAnalysisSnapshotMetadata {
  mode: 'full' | 'quick';
  sourceChapterStart: number;
  sourceChapterEnd: number;
  sourceChapterCount: number;
  sourceTokenCount: number;
  createdAt: string;
}
```

这些字段不影响续写查询逻辑。

## 13.2 激活规则

只有满足全部条件的快照才能激活：

- 运行全部任务成功；
- 五维最终每维不少于 3 条；
- 数据库回读验证通过；
- 无未处理的物化错误。

激活应原子执行：

```text
新快照验证通过
  ↓
在一个事务中切换 active_snapshot_id
  ↓
旧成功快照保留，可用于回滚
```

## 13.3 续写读取规则

AI 续写只执行：

```ts
const snapshot = await getActiveOriginalAnalysisSnapshot(projectId);
const canonContext = await loadCanonContext(snapshot.id);
```

不得：

- 根据 `snapshot.mode` 选择不同查询逻辑；
- 将完整分析和快速分析同时混合；
- 因快速模式而跳过某个五维；
- 因完整模式而额外读取其他表。

对续写而言，当前激活快照就是唯一的原著分析产物。

---

## 14. 状态机建议

```ts
type AnalysisRunStatus =
  | 'planning'
  | 'extracting'
  | 'materializing'
  | 'validating'
  | 'recovering'
  | 'completed'
  | 'failed'
  | 'cancelled';
```

关键约束：

- `completed` 只能从 `validating/recovering` 且五维验收通过后进入；
- `failed` 记录具体失败阶段；
- `completed` 后才能激活；
- 用户取消不得激活半成品；
- 应支持从已完成批次恢复，避免重新分析全部内容。

## 16. 兼容与迁移

## 16.1 旧快照

对历史快照可执行一次健康检查：

- `result_json` 有数据但 Canon 表为空时，尝试重新物化；
- 重新物化后按五维最低数量检查；
- 不满足新标准的旧快照不得被自动标记为新标准下的合格产物；
- 已经激活的旧快照可暂时保留，直到新的分析成功替换，避免用户突然失去续写上下文。

## 16.2 旧快速分析配置

将“最后 30 章”统一迁移为“最后 10 章”：

- UI 文案更新；
- 默认参数更新；
- 实际选择逻辑更新；
- 测试删除对 30 章的旧断言；
- 历史运行记录无需改写，只保留当时的原始范围元数据。

## 16.3 模式字段

模式字段仅用于运行记录和审计。若历史快照无法判断模式，可标记为 `legacy` 或为空，但续写读取不应因此中断。

## 17. 测试方案

## 17.1 单元测试

### 切块规划

- 1M 上下文时正文目标为约 300K tokens；
- 30%不修改模型的 context 和 max output 配置；
- 大输出配置不会被内部 25% 或固定上限截断；
- 完整分析选择全部章节；
- 快速分析只选择最后 10 章；
- 快速范围不足 10 章时选择全部现有章节；
- 快速分析不会为了填充批次加入第 11 章；
- 超长单章能够拆分且不丢正文；
- 重试只缩小正文，不修改 thinking 和 max output。

### 响应校验

- 全数组为空触发重试；
- 有收到条目但 Schema 后为 0 触发重试；
- Schema 有条目但证据后为 0 触发重试；
- reasoning-only 触发重试；
- `finish_reason=length` 触发缩块重试；
- 字段别名可正确归一化；
- 无法解析 JSON 不得保存为成功。

### 五维验收

- 任一维为 0、1、2 均不通过；
- 五维全部为 3 时通过；
- 去重前为 4、去重后为 2 时不通过；
- 原始 JSON 为 3、物化后为 2 时不通过；
- 其他模式或旧快照的数据不得计入当前运行。

## 17.2 集成测试

### 完整分析成功

- 导入多章 TXT；
- 产生多个 30%批次；
- 两路并行完成；
- 五维均达到 3；
- 成功激活；
- 续写能读取新产物。

### 快速分析成功

- 导入超过 10 章 TXT；
- 确认只发送最后 10 章；
- 五维独立达到 3；
- 不读取完整分析数据；
- 成功激活；
- 续写读取方式与完整分析一致。

### 快速分析独立性

- 先建立一个五维丰富的完整快照；
- 快速分析模拟全部返回空；
- 快速分析必须失败；
- 不能因完整快照已有数据而通过；
- 旧完整快照继续保持激活。

### 物化失败

- 模型返回合格 JSON；
- 模拟数据库写入失败或证据失败；
- 运行不得完成；
- 不得激活空快照。

### 定向补扫

- 初次世界规则和剧情线不足；
- 仅针对缺失维度发起补扫；
- 补扫达到最低数量后通过；
- 补扫仍不足时失败且保留旧快照。

## 17.3 回归测试

- 原有暂停、恢复、取消行为；
- API 失败重试；
- 五维页面查询；
- 旧项目打开；
- AI 续写上下文组装；
- 不同服务商 OpenAI-compatible 接口；
- 思考模型同时返回 reasoning 和 content；
- 非思考模型正常 JSON 输出。

## 18. UI 与用户反馈

### 模式文案

**完整原著分析**

> 分析导入 TXT 的全部章节，建立完整五维原著资料。分析将根据模型上下文按 30%正文切块，多轮调用模型以提高质量。

**快速续写分析**

> 精读导入 TXT 的最后 10 章，独立建立可用于续写的完整五维资料。分析仍根据模型上下文按 30%正文切块。

### 进度信息

建议显示：

- 已选择章节数；
- 当前批次/总批次；
- 当前分析路线；
- 是否正在缩块重试；
- 是否正在执行缺失维度补扫；
- 五维当前有效计数；
- 最终不足的维度。

### 失败提示

示例：

> 分析未通过质量验收：世界观规则 2 条、剧情线 1 条，低于每维至少 3 条的要求。系统已完成定向补扫，但仍未达到标准。本次结果未激活，原有成功分析产物保持不变。

## 19. 实施分阶段计划

## 阶段一：模式与范围

- 增加或整理 `full/quick` 模式定义；
- 完整模式选择全部章节；
- 快速模式从最后 30 章改为最后 10 章；
- 确保两种模式创建独立运行和独立快照；
- 移除跨模式继承或合并逻辑。

## 阶段二：切块与模型能力解耦

- 将正文目标改为上下文的 30%；
- 删除大上下文 60%填充等旧规则对正文目标的影响；
- 删除 Canon 专用最大输出硬上限；
- 请求继续使用配置中的完整最大输出；
- 保持 thinking 设置；
- 增加失败批次 20%/12%缩块重试。

## 阶段三：响应和空结果防护

- 加强 reasoning-only、length、空 content 检测；
- 修复全空数组绕过重试的问题；
- 增加 Schema 后为空和证据后为空检测；
- 统一错误码和统计信息。

## 阶段四：物化可靠性

- 以当前运行/快照隔离物化；
- 数据库事务写入；
- 物化后回读；
- 对 JSON 有数据但表为空的情况明确失败；
- 确保五维页面与验收使用一致的有效行过滤规则。

## 阶段五：最终验收与补扫

- 增加五维每维至少 3 条硬门槛；
- 增加缺失维度定向补扫；
- 补扫只使用当前模式的原文范围；
- 失败不激活；
- 成功后原子激活。

## 阶段六：续写读取统一

- 续写只读取当前激活的原著分析快照；
- 删除按 full/quick 分支读取逻辑；
- 验证任一成功模式产物均可无差别用于续写。

## 阶段七：测试与迁移

- 完成单元、集成和回归测试；
- 更新最后 10 章文案和配置；
- 增加旧快照健康检查；
- 验证旧项目不会因迁移直接丢失当前可用产物。

## 20. 完成定义（Definition of Done）

本次改造只有同时满足以下条件才算完成：

- [ ] 完整分析覆盖全部导入 TXT；
- [ ] 快速分析只覆盖最后 10 章；
- [ ] 两种模式不互相读取或借用分析数据；
- [ ] 两种模式都按模型上下文 30%规划原著正文；
- [ ] 30%不修改模型 context 和 max output 配置；
- [ ] 思考模式保持可用且不被原著分析关闭；
- [ ] 不存在 Canon 专用输出硬上限；
- [ ] 两路分析保持并行；
- [ ] 全空 JSON、Schema 后全空、证据后全空均不能成功；
- [ ] JSON 数据能够真实物化并通过回读验证；
- [ ] 五维每维最终至少 3 条有效信息；
- [ ] 最低数量统计严格限定当前运行和当前快照；
- [ ] 缺失维度会执行定向补扫；
- [ ] 补扫失败时运行失败且不激活；
- [ ] 新运行失败时旧成功产物不受影响；
- [ ] 成功快照可原子激活；
- [ ] AI 续写只读取当前激活产物，不区分分析模式；
- [ ] 快速和完整产物均能通过同一续写查询接口使用；
- [ ] 关键路径具有单元测试、集成测试和回归测试。

## 21. Agent 执行顺序建议

1. 先阅读现有原著分析入口、批次规划器、模型请求器、解析器、证据解析器、物化器、快照激活和续写上下文查询链路。
2. 写出当前数据流图和现有测试覆盖，确认修改边界。
3. 先补测试，复现以下失败：
   - 快速模式仍取最后 30 章；
   - 1M上下文正文切块超过 30%；
   - 模型最大输出被内部上限截断；
   - 全空 JSON 被判成功；
   - JSON 有条目但物化后为 0 仍完成；
   - 五维不足 3 条仍激活；
   - 快速分析借用完整分析数据通过验收。
4. 按阶段一至阶段六逐步修改，每完成一阶段运行相关测试。
5. 最后执行完整测试套件、类型检查和构建。
6. 输出变更摘要、关键设计决策、测试结果和仍存在的风险。
