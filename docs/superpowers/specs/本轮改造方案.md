# ShineWriter 原著续写本轮改造方案

> 文档状态：Ready for implementation  
> 编制日期：2026-07-29  
> 适用范围：Android-only React Native 原著续写流程  
> 施工基线：Schema 21、Canon Phase 2、续写生成 Phase 3  
> 建议目标：Schema 22

## 1. 改造结论

本轮同时解决两个会直接影响续写质量与可用性的问题：

1. 将“原著写作风格”提升为原著分析的一等产物。在 Canon 章节分析成功后、激活 Canon 快照前，增加独立的 `style_analysis` 阶段，生成可版本化、可审核、可重试、可失效的原著风格画像。
2. 修正续写章节的用户可见编号与排序。内部继续使用从 0 开始的 `ContinuationChapterPosition`，用户可见章节号从原著续写起点的下一章开始连续编号。

目标流程：

```text
导入原著并设置续写起点
→ Canon 章节分析
→ Canon 证据校验
→ 原著风格分析 style_analysis
→ 风格画像校验
→ 原子激活 Canon 快照与匹配的风格画像
→ Planner
→ Writer（动态注入原著风格）
→ Checker（检查风格漂移）
→ Repair（按违规维度修复）
→ 用户采纳、编辑与定稿
```

这两个改造共享同一个边界事实，但不混用位置语义：

- 原著范围由 `ContinuationSourceSnapshot` 和 `SourceChapterPosition` 决定。
- 新写章节的状态、记忆和失效范围继续使用 `ContinuationChapterPosition`。
- 用户可见章节号只是展示映射，不改变 `chapters.position` 的内部含义。

## 2. 当前问题

### 2.1 原著风格链路未闭环

当前 `continuationStyleService.ts` 存在轻量统计实现，但有以下缺口：

- `extractAndSaveStyleProfile()` 没有实际调用方。
- 只抽取边界前最后 5 章。
- 只有人称、平均句长、段落长度、对话比例等粗粒度数据。
- `ContinuationContextBuilder` 直接按 `project_id` 读表，没有校验画像是否匹配当前 source、版本、hash 和边界。
- Writer 只收到很短的文风说明。
- Planner、Checker、Repair 没有形成一致的风格契约。
- 风格未进入独立 Context 预算和 trace。
- `review_status` 没有真正参与注入决策。
- `styleLevel` 已存在于设置模型，但 UI 没有独立配置入口。

普通流程的笔记仿写已经具备 LLM 五维画像、source hash 缓存、权重合并和 trace。续写可以复用其结构化解析、权重和渲染思想，但不能直接复用 `note_style_profiles` 或 `getOrAnalyzeNoteStyle()`，因为续写必须额外遵守：

- 原著边界隔离。
- source snapshot 一致性。
- Canon 分析任务的暂停、恢复和激活生命周期。
- 不在生成阶段隐式触发额外 LLM 调用。

### 2.2 续写章节编号与原著断开

当前续写章节物理存储在通用 `chapters` 表中，内部 position 从 0 开始，这是正确的数据隔离设计。但用户可见标题仍按 `position + 1` 生成，因此原著在第 20 章结束时，第一篇续写仍会显示“第 1 章”。

此外，新建续写章节使用 `chapters.length` 作为 position。在删除、导入或位置不连续的情况下，可能产生重复或错误顺序。

## 3. 目标与非目标

### 3.1 目标

1. Canon 分析完成后自动产生详细、可操作的原著写作风格画像。
2. 风格画像只读取续写边界内原著，边界之后信息零泄漏。
3. 风格画像与 source 指纹、边界和 analyzer version 绑定。
4. Context 构建只读取缓存画像，不隐式调用 LLM。
5. 根据每个阶段实际 LLM 配置的上下文长度动态调配风格预算。
6. Writer、Checker、Repair 使用同一份冻结风格画像。
7. 用户可以查看、修正、忽略和单独重试风格分析。
8. 新写章节在界面、提示词、导出和通知中延续原著章节号。
9. 保持原著章节与续写章节的内部位置命名空间隔离。

### 3.2 非目标

- 不修改、重写或自动润色原著正文。
- 不保存用于大段复制的原著样本库。
- 不把文风判断混入 Canon 事实表。
- 不为每次生成重新分析原著风格。
- 不将原著 source position 直接写入 `chapters.position`。
- 不因为修改显示章节号而搬移现有状态事件、Story Memory 或生成记录。
- 不在本轮强制升级普通笔记仿写的数据库结构。

## 4. 核心不变量

1. 风格分析只能通过 `continuationSourceReader` 读取 bounded source。
2. 风格样本和证据不得越过 `boundary.charOffsetExclusive`。
3. Context Builder 不得触发 Style Analysis LLM。
4. source id、version、sha256、parser version、normalization version 或边界变化后，旧画像不得注入。
5. Canon 是事实层，Style Profile 是写作约束层，两者分开存储和审核。
6. 生成 run 必须冻结所使用的 style profile id、hash、schema version 和渲染版本。
7. 用户明确的本章要求高于自动风格画像。
8. 原著与续写章节 position 属于两个命名空间。
9. 续写排序以内部 `position ASC, id ASC` 为准，不按标题字符串排序。
10. 用户自定义章节标题不得被自动重编号覆盖。

## 5. 原著风格分析阶段

### 5.1 生命周期位置

在 `canonAnalysisService.processAnalysisRunInner()` 中，将成功路径改为：

```text
chapter_extraction
→ evidence_validation
→ canon_finalizing
→ style_analysis
→ style_validation
→ activateSnapshotAndStyleProfile
```

不得先激活 Canon，再异步生成风格画像。否则会出现 Canon 已 ready、第一轮续写却拿不到文风的时间窗口。

风格分析结果应与 Canon 快照一起发布，但失败策略需要区分事实能力和风格能力：

- Canon 分析或证据校验失败：保持当前阻断行为。
- 风格分析失败：Canon 结果可以保留为待发布候选，但本次分析任务显示“风格分析失败，可单独重试”，不得静默激活一个缺少风格状态说明的完整结果。
- 用户选择跳过文风后，可以显式激活 Canon，active style profile 设为 null。
- `styleLevel='strict'` 且没有 ready 画像时，生成前阻断。
- `styleLevel='balanced'` 且没有 ready 画像时，允许生成，但必须在 UI 和 trace 中明确降级。
- `styleLevel='off'` 时，不影响 Canon 使用。

### 5.2 输入范围

风格分析使用与 Canon run 完全相同的 `ContinuationSourceSnapshot`：

- 相同 source id/version/hash。
- 相同 parser/normalization version。
- 相同 boundary chapter 与 boundary char offset。
- 暂停或恢复时再次执行 `assertSourceStillValid()`。

不得因为完整原著很长而只分析末尾章节。应采用“全量本地统计 + 有界分层抽样”。

### 5.3 全量本地统计

对全部 bounded chapters 执行本地统计，不产生额外 LLM 调用：

- 句长分布，而非只有平均值。
- 段落长度分布。
- 对话比例与对白轮次分布。
- 常用标点与断句模式。
- 第一/第三人称信号。
- 心理、动作、环境和说明性文本的近似比例。
- 章节开头、结尾和转场模式的统计信号。

统计值进入 `metrics_json`，用于：

- 给 LLM 提供全书客观概览。
- Checker 做可解释的偏移判断。
- 在小上下文模型下降级时保留最重要的风格约束。

中文文本统计必须使用适合中文标点和 UTF-16 的实现，避免用简单英文分词假设。

### 5.4 分层抽样

抽样必须确定性、可恢复，并覆盖以下层次：

- 开篇阶段。
- 中段阶段。
- 边界附近阶段。
- 对话密集片段。
- 动作/冲突片段。
- 心理/情绪片段。
- 环境/说明片段。
- 场景转换或章末钩子。

抽样结果只保存引用：

```ts
interface StyleSampleRef {
  sourceChapterId: number;
  sourcePosition: SourceChapterPosition;
  charStart: Utf16Offset;
  charEnd: Utf16Offset;
  contentHash: string;
  sampleKind:
    | 'opening'
    | 'middle'
    | 'boundary'
    | 'dialogue'
    | 'action'
    | 'emotion'
    | 'description'
    | 'transition';
}
```

数据库不保存新的长原文副本。需要查看证据时，通过 SourceReader 按引用读取并再次校验 hash 与边界。

### 5.6 LLM 调用策略

风格分析调用使用 Canon 分析任务冻结的 model config，并记录实际：

- model config id。
- context window。
- max output tokens。
- prompt/completion usage。
- analyzer version。
- source/profile hash。

调用数量根据模型上下文动态决定：

- 抽样材料一次可容纳：一次结构化分析调用。
- 一次无法容纳：拆成若干 map 调用，再做一次 reduce。
- 调用拆分由实际 `context_window`、输出预留、系统提示词 token 和抽样材料 token 计算，不按固定章节数或固定 token 数硬编码。

输出必须经过 JSON Schema 校验。允许一次针对结构错误的修复调用；不得无限重试。

### 5.7 用户修正

自动画像与用户修正分开保存：

- `profile_json`：分析器输出。
- `user_overrides_json`：用户明确修改的维度、权重或禁忌。

重新分析原著时：

- 自动画像可以替换。
- 用户修正不得丢失。
- 如果画像 schema 升级，应迁移或提示用户确认无法映射的修正项。

## 6. Schema 22 建议

### 6.1 版本化风格画像

现有 `continuation_style_profiles` 以 `project_id` 为主键，无法同时保存 staging、ready 和历史版本。建议在 v21→v22 迁移中重建为版本表：

```sql
CREATE TABLE continuation_style_profiles (
  id TEXT PRIMARY KEY,
  project_id INTEGER NOT NULL,
  source_id INTEGER NOT NULL,
  source_version INTEGER NOT NULL,
  source_sha256 TEXT NOT NULL,
  parser_version TEXT NOT NULL,
  normalization_version TEXT NOT NULL,
  boundary_chapter_id INTEGER NOT NULL,
  boundary_position INTEGER NOT NULL,
  boundary_char_offset_exclusive INTEGER NOT NULL,
  analysis_run_id TEXT NOT NULL,
  canon_snapshot_id TEXT NOT NULL,
  profile_schema_version INTEGER NOT NULL,
  analyzer_version TEXT NOT NULL,
  profile_json TEXT NOT NULL DEFAULT '{}',
  metrics_json TEXT NOT NULL DEFAULT '{}',
  sample_refs_json TEXT NOT NULL DEFAULT '[]',
  user_overrides_json TEXT NOT NULL DEFAULT '{}',
  profile_hash TEXT NOT NULL,
  confidence REAL NOT NULL DEFAULT 0,
  state TEXT NOT NULL DEFAULT 'queued',
  review_status TEXT NOT NULL DEFAULT 'pending',
  error_code TEXT,
  error_message TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  completed_at TEXT,
  CHECK(state IN (
    'queued', 'running', 'ready', 'failed',
    'interrupted', 'cancelled', 'outdated'
  )),
  CHECK(review_status IN ('pending', 'confirmed', 'ignored')),
  CHECK(confidence BETWEEN 0 AND 1),
  FOREIGN KEY(project_id) REFERENCES projects(id) ON DELETE CASCADE,
  FOREIGN KEY(source_id) REFERENCES continuation_sources(id) ON DELETE CASCADE,
  FOREIGN KEY(canon_snapshot_id)
    REFERENCES continuation_canon_snapshots(id) ON DELETE CASCADE
);

CREATE INDEX idx_continuation_style_profiles_project_state
  ON continuation_style_profiles(project_id, state, updated_at DESC);

CREATE UNIQUE INDEX idx_continuation_style_profiles_fingerprint
  ON continuation_style_profiles(
    project_id,
    source_id,
    source_version,
    source_sha256,
    boundary_char_offset_exclusive,
    analyzer_version
  );
```

`continuation_settings` 增加：

```sql
active_style_profile_id TEXT
```

`continuation_analysis_runs.stage` 增加：

```text
style_analysis
style_validation
```

风格画像属于备份数据，继续使用 backup format v3，不为本轮升级 backup format。

### 6.2 迁移策略

- 将旧表数据迁移为 legacy profile。
- legacy profile 缺少可靠 source fingerprint 或详细画像时，状态设为 `outdated`，不能自动注入。
- fresh schema、schema manifest、validator、migration fixtures 和恢复顺序必须同步更新。
- 不手改 `version.json`。

### 6.3 激活事务

新增统一激活 API，替代分别更新两个 active pointer：

```ts
activateSnapshotAndStyleProfile(input: {
  projectId: number;
  canonSnapshotId: string;
  styleProfileId: string | null;
  allowStyleSkip: boolean;
}): Promise<void>;
```

同一事务完成：

- 旧 Canon snapshot → outdated。
- 新 Canon snapshot → ready。
- 旧 active style profile → outdated（source/boundary 不匹配时）。
- 新 style profile → ready。
- 更新 `active_canon_snapshot_id`。
- 更新 `active_style_profile_id`。
- 完成 analysis run。
- 将基于旧 active Canon 的进行中 generation run 标记 outdated。

如果事务失败，不得出现只激活其中一项的半成品状态。

## 7. 动态 Context 预算

### 7.1 原则

不得为风格画像写死“500 tokens”“1000 tokens”等固定额度。每个阶段都应基于其实际 LLM 配置单独计算：

```text
stageInputBudget
= context_window
- resolved max_output_tokens
- 实际系统提示词与消息框架 token
- 根据当前窗口和 token estimator 误差动态计算的安全余量
```

Planner、Writer、Checker、Repair 可能使用不同模型，因此不能共用 Writer 的预算，也不能简单使用多个模型中的最小窗口作为所有阶段最终分配。

run 创建时冻结：

```ts
interface ResolvedStageCapacity {
  llmConfigId: number;
  contextWindow: number;
  maxOutputTokens: number;
  promptSkeletonTokens: number;
  safetyTokens: number;
  inputBudget: number;
}

interface ContinuationStageBudgets {
  planner: ResolvedStageCapacity;
  writer: ResolvedStageCapacity;
  checker: ResolvedStageCapacity | null;
  repair: ResolvedStageCapacity | null;
}
```

### 7.2 弹性分配

Context category 使用优先级与效用曲线进行分配：

```text
锁定规则 / hard Canon
> 原著接缝与最近续写
> 当前有效状态和知识边界
> 原著风格画像
> Story Memory
> 历史概览
> 外部补充资料
```

风格画像预先生成多级表达：

- `compact`：人称、叙事距离、基础语气和核心禁忌。
- `standard`：加入句式、对话、描写、节奏和转场。
- `detailed`：加入当前场景变体、参与人物口吻和更完整的禁忌项。

Allocator 根据该阶段剩余空间选择最高可容纳层级，而不是对完整文本做任意字符截断。

大窗口模型获得更完整画像，小窗口模型逐级降档。降档必须写入 trace。

### 7.3 严格度

- `off`：风格候选不进入预算。
- `balanced`：空间不足时从 detailed → standard → compact 降档；仍不足则省略并警告。
- `strict`：先裁剪历史概览和外部补充等软资料；compact 画像仍无法容纳时阻断生成。

超大上下文的费用保护应由用户可配置的最大输入利用率或成本策略控制，不应通过风格模块的固定 token 上限实现。

## 8. 分阶段风格注入

### 8.1 Planner

只注入与规划有关的风格约束：

- 场景节奏。
- 转场方式。
- 信息揭示速度。
- 章末结构。
- 用户明确的风格覆盖。

Planner 不需要完整词汇和句法画像。

### 8.2 Writer

注入：

- 全书基础风格。
- 边界附近风格增量。
- 根据 plan 选中的场景变体。
- 只注入 `participatingCharacterIds` 对应的人物口吻。
- 用户修正和本章明确要求。

优先级：

```text
本章用户明确要求
> 用户保存的风格修正
> 边界附近风格增量
> 原著全书基础风格
> 外部补充仿写笔记
```

提示模型模仿抽象特征，不复制原句。

### 8.3 Checker

Checker 必须获得同一冻结画像的检查契约，至少检查：

- 人称和聚焦方式突变。
- 时态漂移。
- 句长与段落分布明显偏移。
- 对话比例和对白标签明显偏移。
- 原著克制风格突然变成解释性、总结性或模板化 AI 腔。
- 人物口吻明显串位。
- 章末和转场方式严重偏离。
- 与原著存在异常长的连续文本重合。

确定性检查用于明显指标，LLM Checker 用于语气、节奏、口吻等无法仅靠统计判断的维度。

### 8.4 Repair

Repair 只注入发生违规的风格维度和相关修复要求：

- 不因一个风格问题重写无关段落。
- 不修改已通过的 Canon 事实。
- 修复完成后重新运行对应风格检查。

## 9. Context snapshot 与 trace

`ContinuationContextSnapshot` 增加：

```ts
style: {
  profileId: string;
  profileHash: string;
  profileSchemaVersion: number;
  analyzerVersion: string;
  rendererVersion: string;
  sourceFingerprint: string;
  boundaryCharOffsetExclusive: number;
  frozenProfile: OriginalStyleProfileV2;
  userOverrides: Record<string, unknown>;
} | null;
```

Context Builder 必须通过 Style Profile repository/service 读取，不得直接写 SQL。

读取时校验：

- active profile。
- state 为 ready。
- review status 不是 ignored。
- source snapshot 指纹完全一致。
- boundary 完全一致。
- profile hash 正确。

trace 增加 `originalStyle` category：

- 候选与是否选中。
- profile id/hash。
- source/boundary 是否匹配。
- 使用 compact/standard/detailed 哪一级。
- 实际 token。
- 被裁剪或降级原因。
- 风格分析失败、缺失或过期原因。

上下文预览应能看到 Writer 阶段将使用的风格摘要，不能只展示 Planner 请求而让用户误以为 Writer 也使用相同内容。

## 11. 续写章节编号与排序

### 11.1 内部 position 保持不变

继续保持：

```text
chapters.position = ContinuationChapterPosition
```

第一篇续写内部 position 仍为 0。这样不会破坏：

- Story Memory 初始 `throughPosition=-1`。
- 状态事件的 `valid_from_position`。
- 章节修改、删除、回退后的失效范围。
- 续写生成 run 和 artifact 的 target position。
- Phase 1/2 已定义的两个位置命名空间。

### 11.2 用户可见章节号

定义：

```text
sourceBoundaryChapterNumber = boundarySourceChapter.position + 1
displayChapterNumber
  = sourceBoundaryChapterNumber
  + continuationChapter.position
  + 1
```

例如续写起点是原著第 20 章末尾：

```text
续写 position=0 → 第 21 章
续写 position=1 → 第 22 章
续写 position=2 → 第 23 章
```

当没有可用 source/boundary 时，兼容 Phase 1 的离线手写行为，回退为 `continuationPosition + 1`。

### 11.3 统一编号服务

新增独立服务，不允许各页面重复写 `position + 1`：

```ts
interface ContinuationChapterNumbering {
  boundaryChapterNumber: number | null;
  getDisplayNumber(position: ContinuationChapterPosition): number;
  getDefaultTitle(position: ContinuationChapterPosition): string;
  getDisplayTitle(chapter: Chapter): string;
}

getContinuationChapterNumbering(
  projectId: number,
): Promise<ContinuationChapterNumbering>;
```

应覆盖：

- 续写工作台列表。
- 章节编辑器默认提示。
- Planner/Writer 目标章节号。
- Context trace 与预览。
- Story Memory 的用户可见文字。
- 通知和错误信息。
- Markdown/TXT/项目包导出。
- 新建续写章节的默认标题。

### 11.4 新建与排序

新建 position 使用：

```text
nextPosition = max(existing continuation chapter position) + 1
```

没有章节时为 0。不得继续使用 `chapters.length`。

查询与展示排序统一为：

```sql
ORDER BY position ASC, id ASC
```

不得按默认标题或显示章节号的字符串排序。

### 11.5 标题兼容

需要区分自动标题和用户标题：

- 纯编号标题，例如 `第 1 章`、`第1章`，视为可自动重编号。
- 带有用户内容的标题，例如 `第 21 章 夜雨` 或 `夜雨来客`，不得覆盖。

当 source 激活或续写起点改变时：

- 重新计算自动标题。
- 保留自定义标题。
- 不修改内部 position。
- 不搬移状态事件、Story Memory 或 generation run。
- Context/Canon 按现有边界变更规则失效。

长期建议增加显式的 `title_mode='auto'|'custom'`，避免依赖正则猜测；本轮若不增加字段，必须有覆盖中英文空格形式的严格测试。

### 11.6 自定义 offset

即使续写起点位于原著章节中间，新创建的可编辑续写章节仍从该原著章节的下一章编号。原因是原著章节只读，用户续写内容物理存储在新的章节记录中，不能与半章原著共用一个章节号而产生导出冲突。

## 12. 两条改造线的联动

source 或 boundary 改变时：

1. Canon snapshot 失效。
2. Style profile 失效。
3. 进行中的 generation run 失效。
4. 历史摘要按现有规则失效。
5. 续写章节内部 position 不变。
6. 自动标题和用户可见章节号按新边界重算。
7. 用户自定义标题和已写正文不删除。

风格画像与章节编号必须使用同一个 boundary source chapter，避免提示词说“第 21 章”、界面却显示“第 20 章”。

## 14. 测试计划

### 14.1 风格分析单元测试

- 只读取 boundary 内章节。
- 边界位于章节中间时物理裁剪。
- source/boundary 漂移立即 outdated。
- 分层抽样确定性。
- 全量统计覆盖全部 bounded chapters。
- 小窗口 map/reduce 动态拆分。
- 大窗口单次分析。
- JSON 非法、截断和一次修复上限。
- profile hash 与 sample hash 校验。
- 用户修正在重新分析后保留。
- ignored profile 不注入。

### 14.2 动态预算测试

- Planner、Writer、Checker、Repair 使用不同 context window。
- max output 改变时 input budget 自动变化。
- 风格从 detailed 降为 standard/compact。
- balanced 降级有 trace。
- strict 优先移除软资料。
- strict 连 compact 都无法容纳时阻断。
- off 的风格 token 为 0。
- 超大上下文不会套用固定风格 token 上限。

### 14.3 Prompt 与 Checker 测试

- Planner 只收到规划相关风格。
- Writer 收到全局、边界增量、场景变体和参与人物口吻。
- 未参与人物口吻不注入。
- Checker 收到与 Writer 相同 profile hash。
- Repair 只收到违规维度。
- 人称、时态、句长、对话比例和人物口吻漂移可报告。
- 风格问题不会被当作 Canon hard fact。

### 14.4 章节编号测试

- 原著边界第 20 章，首篇续写显示第 21 章。
- 连续新增显示第 21、22、23 章。
- position 有空洞时新建取 max+1。
- 查询按 position、id 稳定排序。
- 修改边界后自动标题重算。
- 用户自定义标题不覆盖。
- 没有 source 时回退第 1、2、3 章。
- custom offset 从所选原著章节的下一章编号。
- Planner、Writer、Context preview、Story Memory、通知和导出编号一致。
- 内部状态事件仍使用 0-based continuation position。

### 14.5 集成与 E2E

- 完整原著分析 → style analysis → 原子激活。
- style analysis 失败 → 单独重试 → 激活。
- 用户显式跳过 style → Canon 可用、trace 明确缺失。
- 边界改变 → Canon/style/run outdated，自动标题重算。
- 连续生成并定稿多章，显示编号、状态事件和 Story Memory 顺序一致。
- 备份恢复后 active Canon、active style profile 和章节显示编号一致。
- 冷启动将 running style task 归一为 interrupted。
