# 本轮改造审查修复方案

> 文档状态：Ready for implementation
> 编制日期：2026-07-30
> 适用范围：Schema 26、Canon/Style 激活、备份恢复、动态预算、续写章节编号
> 目标：修复本轮改造完成后的审查遗留，消除数据丢失、外键失败和半激活状态，再进入 Release 验收

## 1. 修复结论

当前实现的功能主线已经建立，但仍存在三类阻断风险：

1. v25→v26 重建 `continuation_analysis_runs` 时会触发真实 SQLite 的外键重写和级联删除，可能丢失既有 Canon 分析数据并留下指向已删除表的外键。
2. 备份恢复顺序与 `continuation_settings.active_canon_snapshot_id`、`active_style_profile_id` 的父子关系相反，含 active pointer 的备份可能无法恢复。
3. source 删除、切换或 boundary 变化时没有在同一事务中清理 active style pointer，可能造成外键失败或残留过期激活状态。

此外还需修复：

- Canon + Style 激活事务没有真正原子完成 analysis run。
- Style Profile hash 没有覆盖嵌套画像内容。
- 超大上下文仍受到固定 `styleTokens` 上限。
- Prompt、Story Memory 和错误文案仍残留直接 `position + 1`。
- 进度文档与当前仓库状态不一致。

修复优先级必须严格按照：

```text
真实 SQLite 迁移安全
→ 备份恢复与 source 生命周期外键
→ 激活事务
→ profile hash
→ 动态预算
→ 章节编号收口
→ 文档与完整回归
```

P0 未全部通过前，不得构建或交付 Release APK。

## 2. 施工前置检查

开始修改前必须：

1. 阅读 `AGENTS.md`、`README.md`、本方案和 `docs/superpowers/specs/本轮改造方案.md`。
2. 检查当前分支、工作区和最近提交，不覆盖用户未提交改动。
3. 确认 Schema 26 是否已经对外发布：
   - 若尚未发布，可以修正 v25→v26 迁移本身。
   - 若已经发布，不能只改历史迁移；必须增加新的修复迁移，并说明已被错误迁移删除的数据无法凭空恢复，需要从升级前备份恢复。
4. 先建立可执行真实 SQLite 语义的测试或验证入口。仅检查 SQL 字符串、内存对象 schema 或 `executeSql` mock 不视为迁移验收。
5. 不手改 `src/constants/version.json`，不改备份格式版本，除非实际数据格式发生不兼容变化且经过单独评审。

## 3. WP-A：修复 v25→v26 迁移数据安全

### 3.1 问题

当前迁移执行：

```text
ALTER TABLE continuation_analysis_runs
  RENAME TO continuation_analysis_runs_v25
→ 创建同名新表
→ 复制数据
→ DROP continuation_analysis_runs_v25
```

在现代 SQLite 中，父表重命名会同步改写子表外键，使其引用 `continuation_analysis_runs_v25`。删除旧表时，`ON DELETE CASCADE` 会删除 analysis batches 和 Canon 分类数据；子表外键定义还可能继续指向已经不存在的旧表。

### 3.2 修复要求

1. 不得继续在 `foreign_keys=ON` 的普通迁移事务中直接执行当前父表 RENAME→DROP 流程。
2. 采用 SQLite 官方安全重建思路：
   - 在事务外明确控制外键状态。
   - 在事务内创建新表、复制父表数据、替换旧表、重建索引。
   - 必要时同步重建引用该父表的子表外键。
   - 事务提交后恢复 `foreign_keys=ON`。
   - 执行 `PRAGMA foreign_key_check`，任何结果都视为迁移失败。
3. `PRAGMA foreign_keys` 不能在已开启的事务内切换。若现有 `applyMigration/executeTransaction` 无法表达安全流程，应为该迁移增加专用执行器，不要把无效 PRAGMA 塞进现有 statement batch。
4. 迁移前后至少核对以下数据数量和关键 ID 集合不变：
   - `continuation_analysis_runs`
   - `continuation_analysis_batches`
   - `continuation_analysis_work_items`
   - `canon_evidence`
   - 五类 Canon 表
   - 时间线及 evidence link 表
5. 迁移完成后验证子表 `PRAGMA foreign_key_list(...)` 指向 `continuation_analysis_runs`，不得残留 `_v25`。
6. style profile 旧表迁移也要经过相同的真实 SQLite 检查，确认没有新增同类问题。

### 3.3 测试

新增真实 SQLite 迁移测试，至少准备：

- 1 个 project、source、boundary 和 Canon snapshot。
- 1 个 analysis run。
- 多个 batches/work items。
- evidence 和五类 Canon 记录。
- 时间线及 evidence links。
- 旧版 style profile。

断言：

- v25→v26 成功。
- 所有预置 ID 和记录数量保持。
- `PRAGMA foreign_key_check` 返回空。
- 子表外键没有 `_v25`。
- 迁移后可以继续插入新的 analysis batch、work item 和 Canon 记录。
- 故障注入时迁移整体回滚，schema version 不前移。

## 4. WP-B：修复备份恢复与 active pointer 外键

### 4.1 问题

当前恢复顺序中：

```text
continuation_settings             restoreOrder 240
continuation_canon_snapshots      restoreOrder 260
continuation_style_profiles       restoreOrder 510
```

但 settings 引用后两者。插入时 settings 先于父表，删除时父表又先于 settings，均可能违反立即外键约束。

### 4.2 修复要求

优先采用两阶段恢复，避免仅靠一个数字顺序承担 active pointer 环：

1. 清理现有数据前先将 settings 的两个 active pointer 置空，或保证 settings 先于被引用父表删除。
2. 第一阶段恢复 source、source chapters、Canon、style profiles 等父表。
3. 恢复 settings 时暂不写入：
   - `active_canon_snapshot_id`
   - `active_style_profile_id`
4. 所有父表成功插入后，第二阶段回填 active pointers。
5. 回填前验证：
   - Canon snapshot 属于同一 project/source。
   - Style profile 属于同一 project，且其 source/boundary fingerprint 与 settings 一致。
6. 老备份没有 `active_style_profile_id` 时按 `NULL` 处理。
7. 恢复结束执行：
   - `PRAGMA foreign_key_check`
   - schema validator
   - active pointer 业务完整性检查
8. 回滚恢复也必须使用同样的两阶段逻辑，不能只修正正向恢复。

### 4.3 测试

真实 SQLite 备份往返至少覆盖：

- Canon 和 Style 都已激活。
- 仅 Canon 激活、显式跳过 Style。
- Style 已 ignored/outdated。
- 老备份不含新字段。
- 恢复目标库已有另一套 active Canon/Style。
- 正向恢复中途故障后能恢复原数据。

## 5. WP-C：收口 source/boundary/style 生命周期

### 5.1 修复范围

检查并统一：

- `buildActivateSourceBoundaryStatements`
- `updateBoundaryInTx`
- `markAnalysisOutdated`
- `clearActiveSourceAndDelete`
- source replace/import 激活路径
- source delete 路径

### 5.2 统一规则

source 或 boundary 发生变化时，必须在同一事务中：

1. 将旧 Canon 和进行中的 analysis run 按现有规则置为 outdated。
2. 将不再匹配的 style profiles 置为 outdated。
3. 清空 `active_canon_snapshot_id`。
4. 清空 `active_style_profile_id`。
5. 将 generation runs 按现有规则置为 outdated。
6. 更新 settings 和 boundary。

删除 source 前必须先清空所有指向将被级联删除记录的 active pointer，再删除 source。

Context Builder 的 fingerprint 防线继续保留，但不能把它当作数据库状态清理的替代品。

### 5.3 测试

- 激活 Style 后删除 source 成功，外键检查为空。
- 切换 source 后旧 Style 为 outdated，active style pointer 为空。
- 修改 boundary 后旧 Style 为 outdated，active style pointer 为空。
- 旧画像不能注入，strict 模式按设计阻断，balanced 模式按设计降级。
- 故障注入时 source/boundary/settings/style 状态整体回滚。

## 6. WP-D：修复 Canon + Style 原子激活

### 6.1 API

统一激活 API 应携带明确的 analysis run：

```ts
activateSnapshotAndStyleProfile({
  projectId,
  analysisRunId,
  canonSnapshotId,
  styleProfileId,
  allowStyleSkip,
})
```

兼容入口只能做参数解析和委托，不得默认静默跳过 Style。

### 6.2 事务前校验

Style 不为空时必须验证：

- profile 存在且属于 project。
- `canon_snapshot_id` 与待激活快照一致。
- `analysis_run_id` 与本次 run 一致。
- source id/version/hash、parser/normalization version、boundary 全部匹配。
- state 为允许激活的状态。
- review status 不是 ignored。
- profile payload 和 profile hash 有效。

### 6.3 同一事务

同一事务必须完成并验证：

1. 旧 Canon → outdated。
2. 新 Canon → ready。
3. 不匹配旧 Style → outdated。
4. 新 Style → ready，或显式跳过并将 pointer 置空。
5. 更新两个 active pointer。
6. 将指定 analysis run 从允许状态更新为 completed。
7. 使旧 generation runs outdated。

不得再在调用方事务外补写 analysis run completed。

需要为关键 UPDATE 增加可靠的 affected-row 断言；任何应更新 1 行却更新 0 行的情况必须使事务失败。不要只做 Canon 的 post-commit 检查。

### 6.4 测试

- 自动流程从 `running/style_validation` 原子完成。
- 手动审核流程从 `awaiting_review` 原子完成。
- style id 不存在、项目不匹配、snapshot/run 不匹配、fingerprint 不匹配时整体失败。
- style UPDATE 为 0 行时两个 pointer 和 Canon 状态均不变化。
- 激活中每个 statement 位置进行故障注入，不出现半激活。
- 显式跳过 Style 必须有 `allowStyleSkip=true`，trace/UI 明确记录降级。

## 7. WP-E：修复 Style Profile hash

### 7.1 问题

不能使用仅包含顶层字段名的 `JSON.stringify` replacer 数组生成深层 canonical JSON。它会过滤嵌套画像字段，使 hash 无法代表真实画像内容。

### 7.2 修复要求

1. 增加递归稳定序列化：
   - 对对象键递归排序。
   - 数组保持业务顺序；需要无序语义的 sample refs 先按稳定复合键排序。
   - 明确定义 `undefined`、`null`、number 和字符串处理。
2. `profile_hash` 至少覆盖：
   - 完整 profile JSON。
   - metrics JSON。
   - sample refs 的 kind、chapter id、范围和 content hash。
   - profile schema/analyzer version；若不纳入 hash，则必须作为冻结快照的独立一致性字段验证。
3. 用户 overrides 是否纳入基础 profile hash需做明确选择：
   - 若不纳入，冻结 snapshot 必须单独保存 overrides 及其 hash/version。
   - 不允许用户修改 overrides 后 trace 仍无法区分。
4. 注入前不能只校验 hash 正则格式；应重新计算并比较，失败则不注入。
5. 已有错误 hash 的未发布开发数据可以重算；若已发布，应增加兼容升级或将旧画像置为 outdated 后要求重新分析。

### 7.3 测试

- 修改任意 profile 深层字段，hash 改变。
- 修改 metrics、sample range 或 sample content hash，hash 改变。
- 相同内容但对象插入顺序不同，hash 相同。
- 篡改 DB 中 profile JSON 后，balanced 不注入并记录原因，strict 阻断。
- 重新分析保留用户修正，同时 hash/override trace 可区分。

## 8. WP-F：完成真正的动态 Context 预算

### 8.1 修复要求

保留现有按阶段读取 LLM 配置的基础，但移除风格模块的固定 token 封顶：

1. Planner、Writer、Checker、Repair 分别使用自己的：
   - `context_window`
   - `max_output_tokens`
   - 实际 prompt skeleton token
   - 动态 estimator 安全余量
2. `styleTokens` 不得固定 `16_000`；Canon、Memory 等类别的固定 cap 也要审查。
3. 超大上下文费用保护改由以下策略之一控制：
   - 用户可配置的最大输入利用率。
   - 项目级成本策略。
   - LLM config 级输入上限。
4. 若策略尚未开放 UI，应有明确、集中、可配置的默认策略，而不是散落在资料类别中的硬编码绝对值。
5. run 创建时冻结每阶段预算和策略版本；恢复时不得读取新的实时模型窗口替换旧预算。
6. Context trace 记录每阶段：
   - context window
   - output reserve
   - prompt skeleton
   - safety margin
   - style allocated/actual tokens
   - 降档或裁剪原因

### 8.2 测试

- 8K、32K、128K、1M context window。
- 四阶段使用不同模型。
- 改变 max output 后 input budget 联动。
- 1M 模型不再命中固定 16K style 上限。
- balanced detailed→standard→compact→omit。
- strict 先裁剪软资料，compact 仍放不下时阻断。
- off 的风格 token 为 0。
- 冻结 run 恢复后预算不漂移。

## 9. WP-G：章节编号统一收口

### 9.1 修复要求

续写用户可见文字不得再自行计算 `position + 1`。继续通过统一编号服务处理：

- pending bridge。
- seam chapter。
- Planner/Writer 当前目标章节。
- Context trace 和预览。
- Story Memory batch validator、renderer 和错误文案。
- 通知、Toast。
- Markdown/TXT/项目包导出。

通用 `contextBuilder` 若同时服务普通项目和续写项目，应接收可选的 `getDisplayNumber/getDisplayTitle`，续写入口显式传入；普通项目保持 `position + 1` 默认行为。

原著 source chapter 自身的只读编号仍使用 source position，不要误改为 continuation display number。

### 9.2 测试

- 原著边界第 20 章，首篇续写所有用户可见位置均为第 21 章。
- 第二、第三篇续写为第 22、23 章。
- 修改 boundary 后自动标题和所有动态文案同步。
- 自定义章节标题不被覆盖。
- 无 source/boundary 时兼容回退为 position+1。
- 同 position 异常数据仍按 `position ASC, id ASC` 稳定排序。

## 11. 建议提交顺序

建议拆分为可独立审查、可回滚的提交：

1. `fix(migration): preserve canon data in schema 26 upgrade`
2. `fix(backup): restore active canon and style pointers safely`
3. `fix(continuation): invalidate style atomically on source changes`
4. `fix(canon): complete run inside canon-style activation transaction`
5. `fix(style): canonicalize and verify profile hashes`
6. `fix(context): remove fixed style token cap`
7. `fix(numbering): route continuation labels through numbering service`
8. `test(continuation): add real sqlite and lifecycle regressions`
9. `docs: close continuation review remediation`

不要为了提交数量而混合无关格式化。

## 12. 最终验收

完成后必须执行：

```bash
npm run verify
npm run test:coverage
```

并完成真实 SQLite/Android 验收：

- v25 数据库带完整 Canon 数据升级到当前 schema，记录不丢失。
- `PRAGMA foreign_key_check` 为空。
- 含 active Canon/Style 的备份可往返恢复。
