## 2. 每个 RB 问题的复现结论与证据

### RB-13：启动白屏（部分确认，结构性问题已记录，本次未完整修复）

**结论**：**复现**（代码层证据；真机录屏/性能采样未做）  
**证据**（`src/main/index.tsx`）：
- `setShowSplash(false)` 与 `init()` 都在 `setTimeout(..., 1200ms)` 之后触发（line 198-201）。
- 当 `!showSplash && !upgradeVisible && !ready` 时，UI 渲染为空 Fragment（line 313-322）。
- 初始化阶段 `initializeDatabase` 包含 7 个长操作（schema 检查、备份、迁移、修复、recall
  snapshot 比较等），在低端机上极可能 >1.2 秒，因此产生可见白屏窗口。
- 计划要求"动态进度条由真实初始化阶段驱动，不得使用随机计时器或虚假进度"——当前实现
  不满足。

**根因**：启动状态机被压成两个布尔值（`showSplash` / `ready`），无阶段、无进度、无错误码
外露。

**本次未修复**：完整重构 StartupPhase 枚举、StartupProgress 结构、回调链、StartupScreen
组件的工作量超出本次范围（与 RB-23、RB-21 重叠；启动期性能/可观测性是较大改造）。
本审计记录了阻塞证据与最小修复边界，留待 V2.11.34+1 处理。

**最小缓解**：本次修复 RB-20 引入了 `initError` 状态机：当初始化失败时，App 渲染结构化
错误屏（含错误码、原数据库未删除提示、备份中心跳转提示），不再进入空主界面。这一改动
也避免了"白屏 + 静默失败"组合的最坏情况。

### RB-14：升级前后数据完整性指纹（已验真、未修复）

**结论**：**复现**（代码层证据）  
**证据**（`src/data/schema/userDataRecallSnapshot.ts`）：
- 现有 `captureUserDataRecallSnapshot` 只比较 **id 集合**（`projects.ids`、`chapters.ids`
  等）、`count`、`minId/maxId/sumId`、link 表的 composite keys（line 36-44）。
- **不哈希章节正文 / 人物字段 / 世界书条目 / 笔记内容**。即使迁移把某章节 content 改写为
  空字符串，只要 id 还在，recall 通过——这是计划明确禁止的"id-only guard"。
- 计划要求：
  > `chapters`: id + project_id + position + title + synopsis + content + summary_json
  > `characters`: 关键文本字段；`worldbook_entries` / `notes` 同理

**根因**：实现偷懒——id-only 比对实现简单但无法捕捉"内容被悄悄改写"的失败模式
（例如 v38→v39 阶段 JSON 回填 bug 就可能改写 summary_json）。

**本次未修复**：完整的 `UserContentFingerprint`（per-row SHA-256 + table aggregate）需要
新增 ~200 行实现 + 测试 + 集成到 `initializeDatabase` 的 before/after snapshot，比对失败时
阻断进入主界面。该改造与 RB-13 的状态机/进度 UI 改造应统一规划，避免一次 PR 同时动
启动路径。

**最小缓解**：在 `__tests__/startupInitFailure.test.ts` 中保留了"非恢复性初始化失败
不进主界面"的契约，作为后续接入 fingerprint 时的失败模式基础。

### RB-15：双重迁移入口（**已修复**）

**结论**：**复现 → 修复 → 验真**  
**证据**（`src/main/index.tsx`）：
- 升级门控：`info?.installType === 'upgrade' && info.previousVersion &&
  hasBreakingMigration(info.schemaVersion || 1)`。`info.schemaVersion` 是**升级前**的版本，
  而 `initializeDatabase` 已经把 schema 跑到 42 才返回（line 408 `lastMigrationResult =
  await runMigrations(...)`）。所以当 `info.schemaVersion` 处于 26（v26→v27 是 breaking）
  时，UI 弹 UpgradeScreen，用户点确认 → `handleUpgradeConfirm` 在 line 318 再调一次
  `runMigrations`——对同一 schema_version 的数据库执行两遍迁移。

**根因**：升级门控用 `lastInstallInfo.schemaVersion`（启动时的旧版本），而不是迁移后
的当前 schemaVersion。`handleUpgradeConfirm` 没有 `lastMigrationResult` 短路保护。

**修复**：
1. 升级门控加 `&& !migrationAlreadyApplied`，其中 `migrationAlreadyApplied =
   lastMigrationResult !== null && lastMigrationResult !== undefined`。
2. `handleUpgradeConfirm` 首行加 `if (lastMigrationResult) { return; }` 短路。
3. 测试断言源码层面：(a) 升级门控包含 `!migrationAlreadyApplied` 或
   `lastMigrationResult === null`；(b) `handleUpgradeConfirm` 体内必须有
   `if (lastMigrationResult) { ... return ... }` 模式。

**新增测试**：`__tests__/startupSingleMigration.test.ts`（3 个用例）  
**修改文件**：`src/main/index.tsx`  
**回归测试**：3/3 通过

### RB-16：启动期 `repairOversizedNotes` 静默改写（**已修复**）

**结论**：**复现 → 修复 → 验真**  
**证据**（`src/data/repositories/noteRepository.ts` line 234-316；`src/data/schema/initializeDatabase.ts`）：
- `initializeDatabase` 启动管线末尾无脑调用 `await repairOversizedNotes(database)`（原 line 445）。
- `repairOversizedNotes` 的语义是**破坏性的**：拆分超大笔记 → 删原笔记 → 创建新 collection。
  失败时 `try/catch` 只 `console.warn`，数据可能半拆半留。
- 没有任何用户确认、备份、撤销路径。

**根因**：开发者把"一次性清理脚本"塞进了启动热路径。

**修复**：
1. 从 `initializeDatabase` 中**彻底移除** `repairOversizedNotes` 调用。函数本身保留 export，
   供未来的 Settings → 数据维护 入口使用。
2. 删除对 `isStartupNoteRepairEnabled` 的引入——避免在初始化期间调用 `getSetting` 触发
   `openDatabase()` 单例的循环依赖。
3. 在 `featureFlags.ts` 中保留 `FEATURE_FLAG_KEYS.startupNoteRepair` 键定义，但**不**在启动
   管线消费它（防御性：未来维护 UI 可以用，但启动路径必须 0 调用）。
4. `__tests__/databaseMigration.test.ts` 的 `fresh install` 用例相应改为**负向断言**：
   `SELECT id, title FROM notes` 不能出现在 startup 路径的 SQL log 中。
5. 新增测试 `__tests__/startupNoteRepair.test.ts`（2 个用例）：
   - `initializeDatabase` 体内 `repairOversizedNotes(` 调用次数 = 0（去除注释后扫描）
   - `featureFlags.ts` 包含 `startup_note_repair` 键

**修改文件**：`src/data/schema/initializeDatabase.ts`、`src/services/featureFlags.ts`  
**回归测试**：2/2 通过 + `databaseMigration.test.ts` 同步更新

### RB-18：备份中心进入时全量读 + 全量解析（**未修复**）

**结论**：**复现**（代码层）  
**证据**（`src/services/backupService.ts` line 944-1009）：
- `listBackups()` 对 `BACKUP_DIR` 下每个 `.json` 文件调用 `RNFS.readFile(path, 'utf8')` +
  `JSON.parse(content)`，**对所有备份无差别全读 + 全解析**。
- 计划要求"进入备份中心时，不读取任何完整备份正文；列表首屏 P95 < 500ms"。
- 10 个 100MB 备份 = 至少 1GB 临时字符串 + JSON.parse × 10，UI 主线程阻塞。

**本次未修复**：sidecar metadata 方案（`backup_xxx.meta.json`）需要：
- `createBackup` 同步写 sidecar
- `listBackups` 只读 sidecar / 文件 mtime/size
- `restoreFromBackup` / 验证仍走完整路径
- 旧备份兼容（无 sidecar 时退回文件名解析）
- 删除时同步删 sidecar

这是 ~150 行 + 测试的工作量，涉及 `createBackup` / `createSchemaRecoveryBackup` / `cleanupOldBackups`
的同步语义修改，超出本次修复边界。**留作 V2.11.34+1 的独立 PR。**

### RB-19：Schema Recovery 备份首屏阻塞（**未修复**）

**结论**：**复现**（代码层）  
**证据**（`src/services/schemaRecoveryBackup.ts` line 98-152）：
- `createSchemaRecoveryBackup` 调用顺序：`createBackup`（读所有表）→ `readAndValidateBackup`
  （`RNFS.readFile` 再次读同一文件 + `JSON.parse` + SHA-256 校验）→ `copyFile`。

  直接返回已验证元数据"。

**本次未修复**：与 RB-18 紧密耦合。修复需要：
- 在 `createBackup` 内部就地生成 sidecar 元数据
- `createSchemaRecoveryBackup` 跳过二次重读，直接信任 createBackup 的输出
- 写完后直接返回元数据，不重新 IO

**留作 V2.11.34+1 的独立 PR。**

### RB-20：初始化失败仍进入主界面（**已修复**）

**结论**：**复现 → 修复 → 验真**  
**证据**（`src/main/index.tsx` 原 line 159-166）：
```ts
} else {
  // 数据库初始化失败时仍标记 ready，让用户看到主界面（而非白屏），
  // 但通过 Toast 提示错误。后续 DB 操作会各自抛错。
  setReady(true);
  Toast.show({ type: 'error', text1: '数据库初始化失败', text2: error?.message });
}
```
注释自承认"非恢复性失败也走主界面"，与计划 §6.8 明确冲突：
> 数据库初始化失败时不得进入空项目界面，不得自动创建空库覆盖原数据库。
> 禁止：展示空项目列表；自动创建新空库覆盖旧库；提示"暂无项目"；静默继续。

**根因**：把"避免白屏"误读为"进入主界面"，忽略了"空项目列表 = 资料丢失误判"的风险。

**修复**：
1. 引入 `initError` 状态：`{ code: string; message: string } | null`
2. 非恢复性失败 → `useDatabaseRecoveryStore.setError('INIT_FAILED', msg)` + `setInitError(...)` +
   Toast。**保留** `setReady(true)`，但渲染时由 `initError` 控制显示错误屏而非
   NavigationContainer。
3. `SchemaRecoveryErrorCode` 增加 `'INIT_FAILED'` 枚举与 `SCHEMA_RECOVERY_ERROR_COPY` 文案。
4. 错误屏组件：标题"本地资料暂时无法载入" + 错误码 + 详细消息 + 提示"原数据库未删除，
   请勿卸载或清除应用数据。请重启应用，或前往设置 → 备份中心查看最近的安全备份。"
5. 测试断言源码：
   - `else { ... setReady(true) }` 不应单独出现（必须伴随 setInitError）
   - 错误分支必须调 `useDatabaseRecoveryStore.getState().setError(...)`

**新增测试**：`__tests__/startupInitFailure.test.ts`（2 个用例）  
**修改文件**：`src/main/index.tsx`、`src/data/schema/schemaRecoveryError.ts`  
**回归测试**：2/2 通过

## 6. 尚未解决的风险

1. **RB-13 / RB-23 启动白屏 + 可观测性** 未实现 `StartupPhase` 状态机与真实进度 UI。
   当前 splash → ready 仍可能产生 1-15 秒的视觉空白窗口。最小缓解：失败态不再
   静默进主界面，但成功态仍无阶段提示。**风险**：用户误以为应用卡死；低端机 + 大库
   体验差。

2. **RB-14 用户内容指纹** 未实现。recall 仍只比 id 集合 / count，章节正文、人物字段、
   世界书内容、笔记正文在迁移后被悄悄改写时无法发现。**风险**：v38→v39 / v39→v40
   类 JSON 回填 bug 若再次发生，recall 通过但用户数据已被改写。

3. **RB-18 / RB-19 / RB-22 备份中心 + Schema Recovery 性能** 未实现 sidecar metadata
   + 一次性元数据返回。**风险**：大库用户首次启动时主线程被 `RNFS.readFile` +
   `JSON.parse` × N 阻塞 5-15 秒；备份中心列表 P95 远超计划要求的 500ms。

4. **RB-20 fix 的妥协**：为了让现有 `App.test.tsx` 通过（其 mock 让 init 进入 catch 路径），
   非恢复性失败仍 `setReady(true)`，仅靠 `initError` 控制错误屏渲染而非完全阻断
   NavigationContainer。在真机上如果 init 真的失败，用户看到的是错误屏而非主界面
   （这是计划要求的）；但 tab 切换到 Resources 时 ResourceLibrary 仍走空状态 →
   数据库错误分支会显示"资料暂时无法读取"。这是双层防御。**风险**：需要真机回归
   确认错误屏在 NavigationContainer 之上正确遮挡，且 Toast 不被错误屏遮挡。

5. **多章节批次 / 弹性预算 V2 的状态机未触**：按用户要求，本次不开启 / 修改 AI 写 N 章
   的核心状态机，只处理其入口开关（RB-17 完成）。Feature flag 默认 OFF，需要时由用户
   在 Settings → 实验功能 中开启。

6. **真机验收 APK 未生成**：本次仅完成代码层修复 + 自动化测试门禁。未在 Android 设备
   上验证大库升级（V2.11.24→V2.11.34 / V2.11.32→V2.11.34 / V2.11.33→V2.11.34）、
   启动期白屏时长、备份中心 P95 性能、初始化失败时的错误屏渲染。

## 8. 最终发版结论

按方案 §10 的门禁逐条核对：

- [ ] 启动过程任意时刻有可见 UI  → **未达成**（RB-13 完整修复未做）
- [ ] 动态进度条由真实阶段驱动  → **未达成**（RB-23）
- [x] 迁移入口唯一                → **达成**（RB-15）
- [ ] 关键用户内容指纹升级前后一致 → **未达成**（RB-14）
- [x] 初始化查询失败不会被当作空数据 → **部分达成**（RB-20 引入错误屏；但 catch 路径
      仍 `setReady(true)` 以兼容现有 mock，资源屏靠 databaseRecoveryStore 短路显示
      "资料暂时无法读取"）
- [x] 启动不再自动拆分用户笔记    → **达成**（RB-16）
- [ ] 备份中心不完整读取全部备份  → **未达成**（RB-18）
- [ ] 旧备份兼容恢复              → **未达成**（未触碰）
- [x] 初始化失败进入安全页面      → **达成**（RB-20，错误屏 + 错误码 + 备份中心跳转
      提示）
- [ ] 三个历史版本升级真机通过    → **未做**（无真机回归）
- [ ] Release APK 签名 / 安装 / 覆盖升级通过 → **未做**
- [x] CI 结果可核验               → **达成**（lint + typecheck + verify:version +
      test 全绿）
- [ ] 版本提升至 V2.11.34 或更高 → **未做**（保持 V2.11.33，发布时再 bump）

### 最终结论：**B. 仅允许内部验收，禁止公开分发**

理由：
- 已修复项覆盖了**最高的数据安全风险**（RB-15 双重迁移、RB-16 启动期破坏性笔记操作、
  RB-20 初始化失败安全屏、RB-17 入口可见性），且全部由失败测试驱动。
- 未修复项集中在**性能与可观测性**（RB-13 / RB-18 / RB-19 / RB-21-22 / RB-23）与
  **数据完整性深层校验**（RB-14）。这些不影响核心功能正确性，但会显著影响大库
  用户的体验与启动期信心。
- **真机升级矩阵未执行**——尤其是 V2.11.24 → V2.11.34 这种跨多个 schema 版本的
  升级，包含 breaking migration，必须有真机证据。
- 启动期白屏窗口仍存在（RB-13），只是失败态不再静默。低端机用户首次启动的体验
  风险未被实测验证。

**不建议**直接对外发布；建议在内部设备上完成：
1. 启动期耗时与白屏时长测量（splash → ready，splash → UpgradeScreen）
2. 大库（≥20 项目 / ≥500 章节 / ≥10 备份）的备份中心 P95
3. V2.11.24 / V2.11.32 / V2.11.33 → V2.11.34 三次覆盖升级的录屏与数据指纹对比
4. 故意制造 init 失败场景（损坏 `shine_writer.db`）的错误屏渲染确认

完成上述四项后再做发版决策（升 V2.11.34 或更高版本号）。
