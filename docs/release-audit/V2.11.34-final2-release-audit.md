## 2. F2-01 adoptedRevisionId 原子回填 —— 已关闭

### 验真（修复前失败证据）
`adoptPipelineTaskResultAtomic` 的 batch item UPDATE 在语句构建阶段把 `adopted_revision_id` 参数定死为 `null`（注释声称 "resolved via last_insert_rowid below"，但捕获的 insertId 从未回写）。**真实 SQLite 探针：4/4 失败**——adoption 后 `multi_chapter_batch_items.adopted_revision_id` 恒为 NULL。

### 根因
pipeline revision 的 insertId 只在事务执行阶段产生；item UPDATE 的参数在构建阶段已定死。

### 修复
`buildCommitBatchItemAdoptionStatements` 新增 `useLastInsertRowId` 选项，原子路径 SQL 改写为 `adopted_revision_id = last_insert_rowid()`（该 UPDATE 的前一条语句恒为 pipeline-revision INSERT，语义精确）。standalone 路径保持参数化。

### 测试
`__tests__/f201AdoptedRevisionId.test.ts`（4 用例）：有旧正文 / 无旧正文 / 重复 adoption / crash+重试，全部断言 `item.adopted_revision_id === content_revisions.id (source='pipeline', source_ref=taskId)`。修复前 4 失败 → 修复后 4/4。

### 真机对账（N01/N02 批次）
- N01（batch_msj2lh9d_bnkor5）：3 个 item 的 adopted_revision_id = 1/2/3，对应 3 条 pipeline revision，revision.content === chapter.content（matches=1）✓
- N02（batch_msj3os7n_rxisdk）：ord1/2/3 adopted_revision_id = 4/5/6，绑定一致 ✓

## 3. F2-02 Adoption durable close-loop —— 已关闭

### 验真（修复前失败证据）
事务提交后才有 `store.resolveTask()`（fire-and-forget DB 写）与 `markStoryMemoryDirtyIfCovered()`（独立事务）。post-commit JS 全部禁用（resolveTask no-op + markStoryMemoryDirtyIfCovered throw）后：task `resolved_at` 恒 NULL、story memory 不 dirty、pending_invalidated 不落库 —— 4/5 失败。

### 根因
task resolve 与 story-memory dirty intent 都依赖事务后的 best-effort JS 调用，存在 crash window。

### 修复
将两者并入 adoption 同一事务：
1. `UPDATE pipeline_tasks SET resolved_at, resolved_action='accept'`（durable resolve）；
2. 通过已有 `buildStoryMemoryContinuitySideEffects` 纯 SQL builder 追加 dirty / pending_invalidated 语句（事务外读 record、事务内写，幂等 SET）。
事务后保留幂等 backstop（内存刷新 + 兜底 mark）。

### 测试
`__tests__/f202AdoptionDurableCloseLoop.test.ts`（5 用例，post-commit JS 全部禁用）：task durable resolved、story memory dirty、pending_invalidated 侧效果、crash+retry、重复 adoption 幂等。修复前 4 失败 → 修复后 5/5。

### 真机
N01/N02 全部 task `resolved_at` 非空、`resolved_action='accept'`，与 batch item succeeded 同事务完成 ✓

## 4. F2-03 Fingerprint row-key 绑定 —— 已关闭

### 验真（修复前失败证据）
列集不同或 allowlist 激活时 comparator 退化为 per-column sorted aggregates——跨行互换无法检测。**反例测试 2/4 失败**：两行 chapter content 互换 + 新增 summary_json → 误判 pass；两行 worldbook content 互换 + allowlist → 误判 pass。

### 根因
per-column aggregates 丢失行归属。

### 修复
capture 增加 per-row per-column value hash（`rowColumnHashes`）；列集不同/allowlist 时按 BEFORE 列集逐行重算 shared-column hash 比较（rowKey 绑定）。仅 >200k 行上限退化为旧 aggregates（fail-closed 保留）。

### 测试
`__tests__/f203UserContentFingerprintRowBinding.test.ts`（4 用例）：互换+新列 mismatch、互换+allowlist mismatch、合法 collection_id 归一化 pass、新列默认值 pass。修复前 2 失败 → 修复后 4/4。既有 cl03 全绿。

## 6. F2-05 Backup sidecar 限流 + 删除联动 —— 已关闭

### 验真（修复前失败证据）
BackupCenterScreen 用 `Promise.all` 全量并发 backfill（N 个大备份同时完整读取）；`deleteBackup` 不清理 `.meta.json`。修复前（stash 验证）6 失败 / 1 通过。

### 根因
无并发边界；删除只删主文件留 orphan sidecar。

### 修复
`backfillBackupMetaQueued(paths, concurrency=1)` 有限并发队列（单失败隔离、已有 sidecar 跳过）；`deleteBackup` best-effort 同步删除 sidecar；屏幕改用队列。

### 测试
`__tests__/f205BackupSidecarConcurrency.test.ts`（7 用例）：并发 1 时 maxInFlight=1、并发 2 时 ≤2、失败隔离、跳过已有、删除联动、不存在容忍、单文件兼容。修复后 7/7。既有 cl08/backupService 断言同步更新（额外一次 sidecar unlink）。

## 12. 已知限制与剩余风险

1. **模拟器网络不稳定**：真机测试多次出现 `network_error`（"Network request failed"，连接层失败，非 HTTP 429）。DeepSeek v4-flash 并发上限 2500 远高于实际用量，与限流无关。失败处理链路（outcome_unknown → 暂停确认 → checkpoint 恢复）已验证可靠，但生产环境网络质量需真实设备观察。
2. **outcome_unknown 不自动重试**：属于安全设计（结果未知可能已计费），用户确认后现在可从失败 stage 续跑（不浪费已成功阶段）。
3. **npm run test:coverage 阈值缺口**：migrations 目录（v32-v33/v36-v40 等）branches/lines 阈值未达（历史基线）；CI 门禁已切换为 test:ci。覆盖率补全列入后续迭代。
4. **batch 批次最终完成依赖用户驱动**：冷启动后 batch 停在暂停态需用户确认继续（安全设计）；自动化恢复路径由 resume 状态机保证。
5. **lint 基线 warnings（162）**：历史遗留，未在本轮清理。
