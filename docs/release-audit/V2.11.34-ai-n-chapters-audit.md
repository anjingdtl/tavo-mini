## 3. 完整生产链路（Phase 0 重建）

### 3.1 批量创建链路

```
MultiChapterBatchScreen.handleCreate
  → store.createDraftBatch → batchRepo.createBatch + batchRepo.createBatchItem × N
  → store.runPlanner → planner.collectPlannerMaterials + createBatchChapterPlan
    → plannerCompiler.compileBatchPlannerRequest
    → llm.callLLMResult
    → planner.parseBatchChapterPlan (validate / fallback)
MultiChapterBatchScreen.handleStart
  → store.saveEditedPlan → batchRepo.updateBatchItem × N + freezeTailAnchor
    → batchRepo.updateBatchStatus(batchId, 'ready', {startPosition, expectedTailChapterId})
  → store.start → store.driveBatchReconcile (非阻塞)
    → reconcileMultiChapterBatch (主循环)
      → claimBatchLease (CAS, P0)
      → for-loop maxSteps:
        → getBatchById + getBatchItems
        → loadTaskStatuses + loadLatestAttempts
        → determineNextBatchAction
        → executeBatchAction
          → create_chapter → createBatchChapterForItem (txn)
          → create_pipeline_task → createPipelineTaskForBatchItem (txn) + registerPersistedTask
          → run_pipeline / resume_pipeline
            → runChapterPipeline / resumePipeline
              → reconcilePipelineTask (单章 loop)
                → maybeAutoRetryStage (BN-01 关键路径)
                → executeAction → actionRunDraft/Review/FactCheck/Proof/Finalize
                  → runStageAttempt (BN-04 关键路径)
                    → assertBatchBudgetAvailable (BN-04 硬门禁)
                    → createStageAttempt
                    → callReadyLLM → callLLMResult
                    → updateStageAttempt (succeeded/safe_to_retry/outcome_unknown/...)
          → wait_until → 持久化 item.status=waiting_retry + item.nextRetryAt (BN-01/02)
          → adopt_draft_result / adopt_full_result → adoptAndCommit
            → adoptPipelineTaskResult (idempotent fingerprint)
            → commitBatchItemAdoption (txn)
            → setBatchUsageFromRuns (BN-03)
          → pause_* / complete_batch / verify_adoption
```

### 3.2 关键写入点（每个状态的 SQLite 落点）

| 状态 | 写入点 | 表 |
|---|---|---|
| `draft / planning` | store.createDraftBatch + runPlanner | `multi_chapter_batches`, `multi_chapter_batch_items` |
| `ready` (startPosition/expectedTailChapterId 已冻结) | store.saveEditedPlan | `multi_chapter_batches` |
| `running` | run_pipeline / resume_pipeline | `pipeline_tasks`, `pipeline_stage_checkpoints`, `multi_chapter_batch_item_runs` |
| `waiting_retry`（持久化） | wait_until case | `multi_chapter_batch_items.next_retry_at`, `multi_chapter_batches.status` |
| `paused_*` | 各 pause_* case | `multi_chapter_batches`, `multi_chapter_batch_items` |
| `paused_batch_budget` (BN-04) | run_pipeline 捕获 BatchBudgetExceededError | 同上 |
| `completed` | commitBatchItemAdoption (final ordinal) | `multi_chapter_batches.status='completed'` |
| usage (BN-03) | adoptAndCommit → setBatchUsageFromRuns | `multi_chapter_batches.used_*` |

### 3.3 恢复点与所有权

| 触发器 | 入口 | 续租 |
|---|---|---|
| 用户点"开始"/"恢复" | store.start | claimBatchLease CAS |
| UI 看门狗（每 2s） | store.refresh | 仅在 `current.status='waiting_retry' && nextRetryAt<=now` 时触发 start |
| 冷启动 | `pauseInterruptedBatches` + store.loadActiveBatchForProject | 清除死 lease（BN-02/06） |
| 进程崩溃 → 重启 | pauseInterruptedBatches | running/ready-with-traces → paused_user；waiting_retry 保留 |
| lease 过期 | main loop claimBatchLease 失败 | 抛 BATCH_LEASE_CONFLICT → user message |

## 4. BN-01～BN-15 逐项复真结论

| ID | 复现 | 证据（修复前代码） | 修复 |
|---|:-:|---|---|
| **BN-01** | ✅ | `reconcileMultiChapterBatch` 的 `wait_until` 仅 sleep 15_000ms，从不调用 `updateBatchItem(status='waiting_retry', nextRetryAt=...)`；UI 看门狗 `current.status === 'waiting_retry'` 永不触发 | 修复：wait_until 先持久化 `item.status='waiting_retry' + item.nextRetryAt`，再 sleep |
| **BN-02** | ✅ | 同 BN-01；外加 `pauseInterruptedBatches` 把 `waiting_retry` 转为 `paused_user`，要求用户点击"确认后继续"才能继续重试 | 修复：pauseInterruptedBatches 改为对 `waiting_retry` 只清 lease、保留 status |
| **BN-03** | ✅ | `adoptAndCommit` 调用 `incrementBatchUsage(getTaskAttempts(currentTaskId))`——只统计当前 task，旧 task attempts 永不计账；多次 reconcile 时 `incrementBatchUsage` 累加导致重复 | 修复：`setBatchUsageFromRuns(batchId)`——按 `multi_chapter_batch_item_runs.pipeline_task_id` 汇总全集，**SET** 而非累加，天然幂等 + 跨 Task 覆盖 |
| **BN-04** | ✅ | 预算门禁仅在 `determineNextBatchAction` 按章检查；章内 4 次 LLM（draft/review/factCheck/proof）不再校验；已发生 attempt row 但被 budget 阻止的可能性未堵 | 修复：`assertBatchBudgetAvailable` 在 `runStageAttempt` 内、创建 attempt row 之前调用；超限抛 `BatchBudgetExceededError`；run_pipeline case 捕获后持久化 `blocked_batch_budget` + `paused_batch_budget` |
| **BN-05** | ✅ | `getLatestAttemptByTask` 用 `ORDER BY attempt_no DESC, started_at DESC`，attempt_no 仅在 `(task, stage)` 内唯一，跨 stage 取错 | 修复：改为 `ORDER BY COALESCE(completed_at, started_at) DESC, started_at DESC, id DESC` |
| **BN-06** | ✅ | `pauseInterruptedBatches` 不覆盖 `paused_*`；且 `claimBatchLease` 在 paused + lease 未过期时返回 false → 用户"恢复"按钮调用 start 后被 `BATCH_LEASE_CONFLICT` 阻断 | 修复：paused_* 的死 lease 无条件清空（status 保留） |
| **BN-07** | ⚠️ | `adoptPipelineTaskResult` 步骤 2（写 chapter.content）→ 步骤 3（写 pipeline revision）之间崩溃：`chapter.content` 已被覆盖，下一轮恢复时 `oldContent = chapter.content` = 新正文，"前文修订"丢失 | 部分修复：本轮已完成幂等指纹 + adoption 保护链路（既有 fingerprint + `latestRevision.source_ref === taskId` 短路）；**完整事务化留待下迭代**，原因见 §6 |
| **BN-08** | ✅ | `checkProjectTailDrift` 仅比较 `tail position`，不校验 `expectedTailChapterId` | 修复：当 `completedCount === 0` 且 `expectedTailChapterId` 非空时，比对 `tailChapter.id === expectedTailChapterId`；首次采用后停止校验（tail 已变成批次自有章节） |
| **BN-09** | ✅ | `run_pipeline` case 启 `setInterval` 心跳 `claimBatchLease` 与主循环每步续租抢同一 `rowVersion`，两并发必有一个 CAS 失败 → main loop 抛 `BATCH_LEASE_CONFLICT` | 修复：删除冗余 setInterval，主循环独占续租权；长单章运行靠 maxSteps 上限 + pipeline executor 的 fail-closed 兜底 |
| **BN-10** | ✅ | `clearInterval` 不取消正在飞行的异步心跳 → 用户点"暂停"后 finally 块先 release、再 `clearInterval`、但若心跳刚发起且正 await，可能在 release 之后再写 lease | 修复：随 BN-09 一并移除 setInterval 心跳，根因消失 |
| **BN-11** | ✅ | `reconcile.ts` 内多处 `PipelineForeground.start/notifyFailed/notifyComplete/updateProgress` 无条件触发，与 batch 的"单条聚合通知"目标冲突；批量子任务每个都弹通知 | 修复：模块级 `activeForegroundOwner` 在 `reconcilePipelineTask` 入口根据 `options.batchBudgetGate` 切换；所有 foreground 调用经 `shouldEmitForeground()` 闸门 |
| **BN-12** | ✅ | `RunningView` 的 `lastTick` 是 `setInterval(() => setLastTick(Date.now()), 2000)` 本地时钟，与真实持久化进度无关 | 修复：标签值改读 `batch.updatedAt`（来自 SQLite）；新增"已 N s 未更新"提示 |
| **BN-13** | ⚠️ | Flag ON + 用户中途离开 → `ready` 批次在 `pauseInterruptedBatches` 不被清理（无执行痕迹） | 部分修复：本轮在 `pauseInterruptedBatches` 已不再误转 `ready`；**针对 ready 状态加超时清理留待下迭代** |
| **BN-14** | ⚠️ | `store.resume` 对 `waiting_retry / outcome_unknown / blocked_* / failed` 一律走"解绑 → 新 run"，对 outcome_unknown 用户已警示"重复计费"，实际行为无差异 | 部分修复：抽离 `setBatchUsageFromRuns` 后已用 item_runs 完整历史聚合；**对 outcome_unknown 区分"续用同请求"与"新 run"的 UI 入口留待下迭代** |

## 6. 遗留 / 未解决风险

### 6.1 BN-07（adoption 崩溃窗口）的完整事务化
当前 `adoptPipelineTaskResult` 仍是分三步写：旧正文修订 → chapter.content → pipeline revision。已有幂等指纹 + `latestRevision.source_ref === taskId` 短路保护，最坏情况下"前文修订"含新文（见 §4 BN-07 行）。完整事务化需把 createContentRevision × 2 + updateChapter + updateStageCheckpoint 纳入单一 SQLite 事务——本轮未做，因为：
1. 现有指纹已能正确阻断重复采用；
2. 跨表事务涉及外键 + 不同 schema 版本兼容性，需要更全面回归；
3. 当前验证显示"前文修订丢失"风险窗口窄（进程崩溃概率低）。

**下次迭代**将 BN-07 升级为"全事务化 + 指纹二次校验"。

### 6.2 BN-13 ready 状态超时清理
`pauseInterruptedBatches` 不再误转 `ready`，但也没有自动超时清理。建议新增 `cleanupStaleReadyBatches(now)`，将超过 N 小时未进入 running 的 ready 批次转 `cancelled`。

### 6.3 BN-14 outcome_unknown 续用同请求
当前实现是"outcome_unknown 也走新 run"。理想行为：UI 给"续用上次请求"和"重新执行"两个按钮；前者复用 frozen request + 同 task id + 重置 attempt_no 计数。本轮未做 UI 入口拆分，因为涉及 RN 端 `Alert.alert` 多按钮 + store 接口扩展。

### 6.4 BN-15 paused_account_quota 真实换模型后重置
当前 `paused_account_quota` 的"更换模型后继续"复用旧 task，其 `frozen execution` 仍指向旧 model，会立即触发 `OUTLINE_EXECUTION_CONFIG_INVALID`。理想是 `resume()` 检测到 model 已变时主动清理 active_task_id → 触发新 run（与 paused_batch_budget 类似）。本轮未做。
