# 原著续写工作流修复方案

> 适用版本：V2.9.1 / Schema 21  
> 目标：补齐续写工作流的事务一致性、失败重试、用户治理与中断恢复闭环。  
> 原则：不改变原著 Canon 只读边界；不在 SQLite 事务内发起 LLM 请求；不复用旧 freeform pipeline 的阶段语义。

## 1. 结论与优先级

当前续写模块的 Schema、独立 runner、Context、导入和核心单测均已落地，但尚不满足 Phase 3 的完整验收条件。优先处理顺序如下：

1. **P1：定稿与 outbox 的原子提交、失败可重试**，避免定稿章节丢失状态提取与 Story Memory 重建。
2. **P1：补齐用户操作界面**，使 Planner 确认、运行恢复、proposal 审核和重试能够实际完成。
3. **P1：修复模型配置冻结字段与中断恢复状态机**，避免用错模型、恢复失败或永久 `running`。
4. **P1：Source/Canon 变化时使 run 失效，并使 Source 激活原子化**，防止过期 Context 被采纳。
5. **P2：加固 artifact 归属与并发采纳校验**，防止跨 run 正文写入和竞态覆盖。

建议按本文顺序拆为 5 个小提交；每个提交均应配套单测，最后再进行模拟器 E2E 回归。

## 2. P1：定稿、状态提取与 outbox 原子化

### 现状

`finalizeContinuationChapter()` 先提交章节定稿与 Story Memory dirty，再单独写 `extract_state` outbox。若应用在两次提交之间被杀死，章节已定稿但永远没有状态提取任务。

### 修复方案

1. 在 `continuationGenerationRunner.ts` 中解析冻结模型配置后，构造 `extract_state` outbox 的完整插入 SQL。
2. 将以下操作放入同一个 `executeTransaction()`：
   - 更新 `chapters.content/status/finalized_at`；
   - 标记 `project_story_memory` 为 dirty；
   - 更新 `continuation_generation_runs.finalized_revision_hash`（有 sourceRunId 时）；
   - `INSERT OR IGNORE` 写入 `continuation_state_sync_outbox`。
3. 事务提交成功后才异步调用 `processContinuationOutbox({ limit: 1 })`；该调用仅用于加速处理，不能承担可靠投递职责。
4. 将 `enqueueOutbox()` 增加可在外部事务中复用的 statement builder，避免两套 SQL 漂移。

### 验收

- 在 outbox 插入前模拟异常，断言章节、Story Memory、run linkage 全部回滚。
- 重复点击定稿，断言只有一个 `extract_state:<chapterId>:<hash>` outbox。
- 冷启动后存在已定稿章节时，能查到对应未完成 outbox。

## 3. P1：outbox 失败重试与可见性

### 现状

worker 将异常记录为 `failed`，但 `listPendingOutbox()` 仅扫描 `pending` 和 `interrupted`。暂时性的网络、配置或模型错误会永久停留在失败状态。

### 修复方案

1. 保留 `failed` 状态和 `last_error`，不要把失败伪装为成功。
2. 新增 repository 方法 `retryContinuationOutbox(id)`：
   - 仅允许 `failed` 或 `interrupted`；
   - 原子重置为 `pending`、清空 `last_error`；
   - 保留 `attempt_count` 作为审计信息。
3. 新增 `retryFailedContinuationOutbox(projectId, limit)`，供冷启动和“全部重试”使用；建议只重试可恢复错误，配置缺失等错误保留给用户手动处理。
4. 为每个 project 提供 outbox 摘要：待处理数、失败数、最近错误和重试按钮。
5. `processContinuationOutbox()` 可继续只领取 `pending/interrupted`，避免自动无限重试和重复计费；自动重试必须有退避与最大次数。

### 验收

- `extract_state` 因网络失败后，用户点击重试可成功生成 proposal。
- `rebuild_story_memory` 失败后重试不重复 state event。
- 重试同一 outbox 两次，只有一个 worker 成功 claim。
- UI 可展示失败原因，但不得显示完整 prompt、正文或 API Key。

## 4. P1：用户治理与恢复界面

### 现状

`ContinuationResultScreen` 只有“采纳为草稿”和“放弃”。以下已实现的服务能力没有界面入口：

- `confirmPlanAndContinue()`；
- `resumeInterruptedRun()`；
- `confirmProposal()` / `rejectProposal()`；
- outbox 失败重试。

这会导致 Planner 策略为 `always` 或命中风险确认时无法继续；章节定稿后的 proposal 也无法由用户确认并回灌状态。

### 修复方案

1. 扩展 `ContinuationResultScreen` 的状态分支：
   - `awaiting_user` 且存在待确认 plan：展示计划全文、风险项、“确认并继续生成”和“放弃”；
   - `interrupted`：展示最后完成阶段、“从此阶段继续”和“放弃”；
   - `failed`：展示简短错误和“重试/重新发起”建议；
   - `outdated`：明确禁止采纳，提供“按最新 Canon 重新发起”。
2. 新建 `ContinuationStateReviewScreen`（或在续写首页增加“状态待确认”入口）：
   - 按章节列出 pending proposal；
   - 展示 proposal 类型、正文定位、摘要、关联实体与影响等级；
   - 提供确认、拒绝、填写决策备注；
   - 仅确认操作调用 `confirmProposal()`。
3. 新建 `ContinuationSyncStatus` 区块：展示 outbox 的 pending/failed 状态，并提供单项或批量重试。
4. 所有异步按钮需防重复点击；完成后 reload 当前 run/proposal/outbox 数据。

### 验收

- Planner confirmation policy 为 `always` 时，用户确认后能进入 Writer。
- app 被杀死后，`interrupted` run 可从持久化阶段边界恢复。
- 定稿后 proposal 可被确认，生成 state event 并触发 Story Memory rebuild。
- strict 模式在存在 major pending proposal 时显示明确去向，不出现无操作可选的阻断。

## 5. P1：模型配置冻结与中断状态机

### 5.1 修复冻结字段名

`finalizeContinuationChapter()` 当前读取 `resolvedLlmConfigIds`，但 Context snapshot 的权威字段为 `resolvedModelConfigIds`。

修改为：

```ts
const settingsSnapshot = JSON.parse(sourceRun.settingsSnapshotJson);
frozenStateExtractionConfigId =
  settingsSnapshot.resolvedModelConfigIds?.stateExtraction ?? null;
```

对损坏或旧快照继续安全回退为 `null`，但应在 outbox 的可见错误/日志元数据中留下“未取得冻结配置”的原因，不记录正文。

### 5.2 重构恢复入口

当前 `resumeInterruptedRun()` 在“已有 plan、尚无 artifact”的 Writer 中断场景直接调用 `confirmPlanAndContinue()`；后者只接受 `awaiting_user`，因此必然失败。

建议抽出内部函数：

```ts
resumeFromWriter(run, snapshot, plan, options)
```

恢复逻辑应为：

| 最后持久化阶段 | 恢复动作 |
| --- | --- |
| `context` / `planner` | CAS `interrupted → running`，重新执行 Planner |
| `writer` 且存在 plan、无 artifact | CAS 后直接从 Writer 执行 |
| `checker` / `repair` 且存在 artifact | 从最近 artifact 恢复检查或修复；不能把半截网络流视为完成 |
| 已有可采纳 artifact | CAS `interrupted → awaiting_user` |
| `awaiting_user` | 保持等待，无需重新调用模型 |

所有恢复分支必须使用与 `startContinuationRun()` 相同的 `try/catch/finally` 收口：取消写 `cancelled`，异常写 `failed`，最后清理 `activeControllers`。恢复中不得遗留永久 `running`。

### 验收

- 分别在 Planner、Writer、Checker、Repair 四阶段模拟崩溃并恢复。
- Writer 调用失败后，run 最终状态为 `failed`，不是 `running`。
- 续写四阶段与 State Extraction 都使用 run 创建时冻结的 config ID。

## 6. P1：Source/Canon 失效与 Source 激活原子性

### 6.1 Source/Canon 改变时失效 run

`outdatedRunsOnSourceOrCanonChange()` 已存在，但当前没有调用点。必须在以下成功提交后调用或合并到同一失效 helper：

- `confirmContinuationSource()` 成功切换 active source/boundary；
- 原著 Source 替换或删除；
- Canon snapshot 激活、revision 变化、active snapshot 失效；
- 续写边界变化。

失效范围限定为该 project 且状态为 `queued/running/awaiting_user/interrupted` 的 run。`adoptArtifactAsDraft()` 除了检查 `run.state !== 'outdated'`，还应在事务前复查当前 source ID、Canon snapshot ID/revision 与 run 快照一致；不一致则原子标记 outdated 并拒绝采纳。

### 6.2 Source 激活使用单事务

当前 Source 状态切换与 `continuation_settings` 指针更新分两次提交。改为在一个 `executeTransaction()` 中完成：

1. 旧 `ready` source 改为 `superseded`；
2. 新 source 改为 `ready`；
3. 更新 `continuation_settings.active_source_id`、边界字段和 `analysis_status`；
4. 更新 import job 为 `completed`；
5. 对未完成 continuation run 写 `outdated`。

不要在事务内执行文件删除、LLM 或 UI 通知；私有导入副本删除仍在事务成功后 best-effort 执行。

### 验收

- 在 Source 激活的每条 SQL 前注入失败，断言数据库不会留下“settings 指向 superseded source”。
- run 处于 `awaiting_user` 时更换 Source 或 Canon，采纳被拒绝并提示重新发起。
- 旧 artifact、check 和 plan 可保留审计，但不得继续作为当前 Context 的产物采纳。

## 7. P2：artifact 归属与采纳并发保护

### 现状

`adoptArtifactAsDraft({ runId, artifactId })` 按 ID 读取 artifact，未校验 `artifact.runId === runId`。另外，读取章节 hash 与事务写章节之间存在并发窗口。

### 修复方案

1. repository 提供 `getArtifactForRun(runId, artifactId)`，SQL 必须同时匹配 `id` 与 `run_id`。
2. 采纳事务中的 run 更新使用 CAS；若影响行数为 0，整笔事务必须失败，不能只写章节。
3. 章节更新加入乐观并发条件：将读取到的 `updated_at` 或原 content hash 带入 `WHERE`。若冲突，抛 `ContinuationConflictError`，由 UI 决定是否强制覆盖。
4. force overwrite 必须只放宽正文 hash 校验，不能放宽 run、project、chapter 或 artifact 的归属校验。

### 验收

- 传入其他 run 的 artifact ID 必须被拒绝。
- 采纳同时发生取消/放弃时，章节内容不被错误覆盖。
- 用户编辑章节与采纳并发时，默认走冲突提示；明确确认覆盖后才写入。

## 8. 测试与发布门禁

新增或补强以下测试后，再运行完整门禁：

```powershell
npx jest __tests__/continuationPhase3Core.test.ts __tests__/continuationPhase3Pipeline.test.ts __tests__/continuationPhase3Repository.test.ts --runInBand --ci
npm run typecheck
npm run lint
npm run test:ci
npm run test:coverage
npm run apk:debug
```

新增测试最低覆盖：

- finalize + outbox 的事务回滚、幂等和冷启动恢复；
- outbox failed → 手动重试 → completed；
- Planner 确认、Writer 中断恢复、失败终态化；
- 冻结 State Extraction 配置 ID；
- Source/Canon 变化阻止采纳；
- Source 激活事务故障注入；
- proposal 确认/拒绝 UI 与事件/outbox 一致性；
- artifact 跨 run 拒绝与采纳竞态。

E2E 需补充：Planner 确认、应用重启后恢复、outbox 失败重试、proposal 确认、Source/Canon 更新后旧 run 失效。真实设备还应覆盖在线模型与本地模型各一条完整闭环。

## 9. 完成定义

以下条件同时满足，才能将本次续写工作流标记为“完成”：

1. 定稿、dirty 标记和 outbox 具备原子一致性；失败任务可审计、可重试。
2. 用户可以完成 Planner 确认、续跑、采纳、proposal 确认/拒绝与失败处理。
3. 所有阶段严格使用 run 创建时冻结的模型配置。
4. Source、边界或 Canon 改变后，过期 run 不能生成、继续或采纳。
5. 中断与失败不会留下不可恢复的 `running` 状态。
6. 跨 run artifact 与章节并发修改不能造成误写。
7. 单测、覆盖率、Debug APK 与新增 E2E 全部通过，并完成至少一轮真机在线/本地模型验证记录。
